## 实际发现与修复

1. **成果宿主路径误导模型。** 原资料同时给正文和 `assets/...` 宿主路径，而这些路径不在 Agent 的虚拟工作区。普通 API 与 Harness 的行为测试先复现，再修复 model_input，只传正文及可引用元数据，原文件/哈希/清单保持。
2. **组织决策被通用文件工具带偏。** 模型反复读取其他任务的私有草稿，甚至复制已有内容。现在通过 SDK 原生 excluded_tools 收敛组织轮次，保留必需安全中间件；成员工作仍有虚拟文件工具。组织会话键升级避免继续错误探索，成员文件会话兼容，旧检查点保留。
3. **后续排程仍要求模型操纵内部岗位 ID。** 真实失败包括漏 position_id、把成果 ID 当工作 ID。新增 schedule_work 接受成员姓名/ID和已有任务标题/ID或成果ID，宿主解析唯一任职、生成新工作ID及依赖，再提交原 create_work 操作。歧义、缺失、重复标题、身份/岗位覆盖拒绝；当前权限和版本仍由原 Engine 校验。
4. **等待时间易出错。** 新增 wait_for_event，用原因及1–86400秒间隔，由宿主计算 UTC 复查时间。原 update_organization 保留。

接口改动没有改Engine的授权、金额、未知核对或事务机制。单次派发仍至多一次真实请求，终结工具仍需单独调用。实际已证明新排程可采用、接着派发，并能提交等待；尚不能证明任务最终质量、事件成功处理或稳定自治。模型对私有草稿路径的错误认识和仅交摘要的问题未被虚构成已解决。
