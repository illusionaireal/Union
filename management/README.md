# 项目管理手册

当前入口：[项目总览](../PROJECT.md) · [工作看板](../TASKS.md)。适用于 AI-UNION 项目及 ai-union-corp 的筹建协作；这是一套可修订的起始约定，不是平台强制所有组织采用的制度。

## 路线镜像与运行态来源

`project.json` 是仓库内的路线、模块成熟度和证据镜像；PROJECT.md 的三个标记区及 TASKS.md 由它生成。它不再裁决实际认领、运行态或 WIP。

**UNION Kanban API 是唯一运行态来源**：任务认领、`progress/review/blocked/done`、负责人、实时依赖、评论、交付和 WIP 都先在看板发生。仓库仅在交付提交中同步长期路线、规格与证据链接，不能反向用旧的 `started_at` 或本地数量阻止一个看板可认领的任务。既有 `specs/*/tasks.md` 保留迭代实施检查，不另立当前优先级。

```sh
npm run management:status  # 只读状态、就绪事项和阻塞
npm run management:render # 修改主账后重新生成总览和看板
npm run check:management  # 验证规则、视图一致性及管理测试
npm run check            # 已包含管理检查及原有工程检查
```

例：认领任务时先通过 Kanban API 读取版本并认领；收到 200 后才开始。交付时先把分支、提交/PR、验证和已知限制写入看板，再在仓库提交中补充长期证据。`project.json` 的状态只表示路线镜像是否需要更新，不能覆盖看板状态。所有修改随 Git 提交，变更历史用于追溯；本地检查不是防篡改、权限或 WIP 系统。

新卡片格式见 [task.json](templates/task.json)。先复制字段，使用未占用的 U 编号，明确验收条件；不得直接将占位卡加入主账。字段中的路径从仓库根开始，无外部链接或凭据。

## 工作约定

| 状态 | 使用条件 |
| --- | --- |
| candidate 候选 | 有想法，是否做尚未决定 |
| backlog 待依赖 | 已纳入路线，依赖或具体准备未完成 |
| ready 就绪 | 验收条件明确，任务依赖均完成，可以认领 |
| doing 进行中 | 路线镜像中的实施记录；实际认领以 Kanban 为准 |
| blocked 阻塞 | 写明原因、解除动作及解除负责人；未认领负责人必须显式为空 |
| review 待验收 | 路线镜像中的验收记录；实际评审队列以 Kanban 为准 |
| done 完成 | 验收范围、验收者、证据和结论齐全；任务依赖均完成 |

Kanban 服务端应从实时 `progress` 卡片计算 WIP，并在状态迁移时校验上限；`blocked`、`review` 和仓库历史 `started_at` 不得隐式占用开发槽位。若要设置团队或个人上限，配置与拒绝原因必须由 Kanban API 返回，不能由仓库生成脚本猜测。

`owner` 是实际承担者，`role` 是需要的责任。公司未成立时，外部工程代理必须标明自己的身份，不能填写不存在的公司成员。`completion.reviewer` 如为实施者自检须明确说明；涉及权限/金额的独立复核仍按仓库既有要求执行。

完成范围为 `documentation` 文档、`controlled` 受控验证、`real` 指定真实场景、`sustained` 指定持续运行。工具只能检查记录是否完整和证据文件是否存在，不能判断内容真实性、业务质量、身份或授权；验收者负责实际审阅。实际尝试失败可以形成已完成的诊断任务，但原目标验收保持未通过。

里程碑不按勾选数或任务平均进度自动升级。只有退出条件均有相符证据才能改为 `accepted`，填写 `reviewer` 和 `accepted_at`；G0 的 `baseline` 仅表示工程底座已有。不将统计出的任务完成率作为产品完成度。

## 每次交付与评审

1. 选取对当前目标最有价值的就绪项，认领后开工；遇阻塞先留记录。
2. 保留可审查成果及测试/运行证据，注明人工帮助、费用未知和未验证范围。
3. 验收者核对该项标准，更新主账、生成视图，再提交变更；STATUS/HANDOFF 只写本次变化。
4. 每个阶段或每周做一次短评审，复查已交付、失败、阻塞、资源与下一工作批次。使用 [review.md](templates/review.md)，本轮样例见 [首次评审](reviews/2026-10-28.md)。目前没有定时任务。

## 自我改进如何进入工作

重复失败、交接等待、状态矛盾、目标停滞等，都是改进信号。组织应能从运行反馈中提出假设并安排改进；责任与触发方式可自行形成，不规定固定管理岗位或复盘 Agent。

使用 [improvement.md](templates/improvement.md) 留下：问题证据 → 原因假设 → 可选方案 → 有限试验 → 结果比较 → 采用/调整/撤回 → 后续观察。必须标注发现来源是组织自主、外部提醒还是预设脚本。例行填写复盘表不等于自主改善。

工具选型先比较流程调整/现有工具、开源、自建和采购；看需求匹配、接入和维护成本、数据/权限、退出能力。先做能检验假设的小范围试验，使用 [tool-decision.md](templates/tool-decision.md)。不要求每次改进都装软件，更不把自建工具当成功指标。

真实效果的验收方法见 [SELF_IMPROVEMENT.md](SELF_IMPROVEMENT.md)。该协议已准备不代表公司已具备或通过这种能力。

## 公司接管与工具迁移

当前管理主账由外部工程维护。公司只有在实际成立、可读这些资料、在宿主授予的范围内能提出/保存修改，并有责任交接和真实回执时，才算接管。U-018 核查现有观察与调整接口，U-019 验收真实改进；本轮没有给成员自动增加仓库访问权。

公司可以提出改用现有开源或采购管理工具，也可以修改本手册。迁移需明确新的唯一主账，保留 U 编号、负责人、依赖、证据链接与历史，实际核对一次导入/导出及回滚；停用旧主账编辑后再切换。平台负责接入和实际权限控制，组织负责工具选择及效果。既有章程/资源/采购授权边界不因写入管理卡片而扩大。
