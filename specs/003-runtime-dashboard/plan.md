# Dashboard 实施计划

状态：2026-10-12 已作为 004 的观察模块实现并完成本地 fixture 验收。依据 [spec.md](spec.md)，证据见 [004 验收记录](../../evidence/004-organization-console/README.md)。

本计划为 004 操作工作台的观察子模块。后续工程优先级、写操作与授权按 [004 实施计划](../004-organization-console/plan.md)推进；不再把只读看板视为完整产品交付。

## 实现方向

1. 保留已有单 HTML 开发展示页，新增单 HTML 运行看板与同源只读观察服务。单文件约束适用于前端；实时数据需要连接运行时服务。
2. 基于现有记录定义观察契约，参考 `status / events / decisions / usage / context` 的字段语义。基线 `status()` 的多次独立读取和 running 误报已修正；观察层采用单次只读事务，并用匹配执行 owner 的心跳和锁证据区分正常在途、活性未确认与未知结果。
3. 显式指定组织根目录，使用只读连接及字段白名单。读取过程不调用 runner、恢复、派发或唤醒逻辑；成果单独按登记 ID 读取并校验，错误保留为可解释状态。
4. 前端提供总览、成员岗位、工作详情、成果、事件决定和资源执行视图；实际每 4 秒轮询及手动刷新，满足不超过 5 秒的要求。定义服务实例标识、组织 ID 和请求／快照顺序，采用有超时的刷新和旧响应丢弃规则；不以组织状态版本判定数据是否更新，因为新增事件、拒绝决定和 begin_decision 不增加该版本。
5. 观察服务默认本地使用，组织数据不加入公开站点或静态发布包。后续远程部署需要单独实现访问控制。

## 开发顺序

- 先以 [PRD](../../docs/PRD.md)、[产品设计](../../docs/product-design.md)和高保真原型形成产品与页面基线，再定义契约、实现一致只读的观察接口及实际视图。
- 以确定性 fixture 验证关联、阻塞和数据更新；不依赖真实模型调用或 Cloudflare 发布条件。
- 完成错误与恢复处理、单 HTML 交付、验证记录及运行文档，再进行首版 Dashboard 验收。
- 有限真实 Codex 试跑仍是独立的真实能力验证事项，Dashboard 开发不消耗模型预算。

## 验证

对只读无副作用、字段隔离、快照一致性、成果校验及错误处理编写行为测试。增加正常慢执行器仍活跃的观察、同版本事件和决定执行变化、同版本响应乱序、服务重启与超时场景（A09、A10）。浏览器验证实际刷新、断开恢复、跨组织切换、筛选、成果下载、键盘与手机布局。运行 `python -m unittest discover -v` 和 `node scripts/check_console.cjs`，实际结果统一记录在 `evidence/004-organization-console/`；设计检查另记在 `evidence/design/`。
