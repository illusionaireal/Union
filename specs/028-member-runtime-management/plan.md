# 下一开发任务：成员执行与托管管理

2026-10-30 · 基线 `dev@66a1f69` · 本次仅规划，尚未实现。

目标：能够明确回答“每名员工由哪里执行、当前做什么、进度保存在哪里、服务中断后如何接续”，并为单 AU 在已有 Linux 主机上持续运行建立受控托管入口。

## 1. 采用的部署方案

首版使用一台持久 Linux 主机，平台控制台、AU 执行服务和 New API 分开运行。一个 AU 同时只有一个有效派发器；员工共享 Harness 实现，按成员身份和任务会话隔离上下文。平台可托管，也可登记用户自行部署的 AU；外部服务没有控制接口时只展示已知资料，不开放启停。

| 对象 | 放在哪里 | 生命周期与边界 |
| --- | --- | --- |
| 员工身份、岗位、正式工作与成果 | AU 的持久存储 | `(au_id, member_id)`；换进程不换员工；不创建另一套人员表 |
| Agent Harness | AU 执行服务 | 复用 Deep Agents；按任务唤醒和接续；空闲等待不调用模型 |
| 会话、检查点和虚拟草稿 | AU 私有持久目录 | 任务/任职/章程/模型连接版本决定恢复范围；不是跨任务长期记忆的替代品 |
| 业务工作区 | 宿主授权的隔离环境 | 首版复用现有按命令启动的 Docker 容器及团队共享业务目录；不宣称成员级文件隔离 |
| 模型 | 上游供应商，通过 New API 或自有连接调用 | 不在网关部署员工；本批沿用 AU 默认连接，员工分别选模型后续按需扩展；不强制经平台网关 |
| 持久托管 | 本机 systemd + 现有 `ai_union.service` | 扩展已有有限运行/重启策略；部署和资源授权独立于组织章程 |

新增员工沿用组织自组织流程，默认使用 AU 的有效执行环境；不要求管理员为每位员工手动部署容器。不需要编程的岗位可以只有模型和业务工具。浏览器登录态、专属长驻应用和成员专用沙箱按真实需求另行接入。

## 2. 核查结论：复用什么、补什么

| 当前已有 | 本批新增 |
| --- | --- |
| `runner.py`：组织级文件锁、串行派发、空闲等待、unknown 阻断 | 统一运行位置和活性描述，服务所有者与当前任务的可追溯关联 |
| `harness.py`：按成员/任职/任务及版本生成会话键，SQLite 检查点 | 只读会话摘要，不向网页或其他成员暴露消息、虚拟文件、检查点内容 |
| `activity.py`：心跳与持锁组合确认活性 | 区分稳定 runtime_id、每次启动的实例标识和当前执行 owner；旧心跳/旧实例不能证明新运行活性 |
| `service.py`、`ops/systemd/`：有限 watch、预算到限/unknown/暂停阻止自动重启 | 通用 AU 服务绑定、受限控制适配、异步运维回执和安全停止边界 |
| `workspace.py`：宿主/章程/岗位联合授权、无网络容器、未知命令核对 | 当前工作是否获准使用工作区的摘要及阻塞原因；保留目录与镜像配置在宿主 |
| Members/Resources 页面及已有 start/pause/reconcile | 员工执行视图和 AU 托管摘要；托管模式下统一运行入口，避免两个派发器竞争 |

当前并非“一名员工一个常驻进程”，也没有远程 Worker 池或同 AU 并行调度。当前工作区是组织级共享目录，不在本批将其改称员工私有磁盘。

## 4. 第一批 U-041：观察与运行位置

建议新增 `ai_union/runtime_view.py`，对既有 Engine、runs、agent_sessions、host_activity、workspace binding 做只读投影；必要的静态部署描述由受信宿主 CLI 保存。`observation.py` 扩展 AU 快照，前端沿用同源 API、组织范围及乱序保护。

- 稳定 `runtime_id` 表示安装/运行位置，进程重启产生新 `instance_id`；保留 `run_id` 与现有 `host_owner` 的关联，不能用 PID 或姓名当员工身份。
- 首版执行拓扑保持每 AU 一个有效派发器、并发1。`embedded` 表示控制台有限作业；`managed_local` 表示本机托管服务；`external` 仅表示外部登记。填写部署模式不证明在线。
- 成员摘要显示当前/排队工作、活跃任职、最近执行、任务会话是否可接续、工作区能力与明确原因。对没有工作、等待依赖、暂停派发、预算耗尽、未核对执行分别表达。
- 运行位置与工作状态分列；“没有在执行”不等于员工不存在，“任务可接续”不等于远程请求已安全结束。筹建/组织决策轮单独显示，不伪装为普通员工工作。
- 观察者沿用本 AU 公开快照范围；私有路径、PID、原始日志、模型密钥、board key、检查点正文不进入新投影。成员 Agent 不因看板增强自动获得平台工具。
- 只读请求不写心跳、不调用 recover、不触发模型、容器或 systemd。旧实例无描述时显示“部署位置未登记”，读取旧数据库不写伪造的绑定。

代码落点：`activity.py`、`observation.py`、拟新增 `runtime_view.py`，按需要读取 `harness.py` 的会话记录；React `api/types.ts`、`pages/Members.tsx`、`pages/Resources.tsx` 和成员详情。具体公开契约见 [spec.md](spec.md)。

## 5. 第二批 U-042：托管控制

在已有持久服务基础上增加 `runtime_control.py`，由宿主将 `runtime_id → AU目录/服务单元/资源边界` 绑定为私有配置。网页只提交 runtime_id、动作、基准版本、幂等请求ID及依据，不能提交宿主路径、systemd unit 字符串、镜像、shell 或任意命令参数。

首个适配器支持本机 Linux/systemd 固定服务单元。系统级服务继续使用现有专用 `union` 用户；控制权限通过宿主安装的固定对象规则提供，具体规则随实现一并测试和独立复核。控制台不得取得通用 sudo、任意 systemctl 或 Docker socket 权限。没有该能力时只提供观察和宿主操作说明。

两类权限分开：组织 board 控制自己 AU 的派发/资源；宿主显式授予 `runtime_manage` 才能控制登记的服务。调用模型的启动/恢复同时满足 AU 运行授权和累计资源条件。027 的 `--enable-gateway-management` 不隐含 runtime_manage；AI 成员没有默认运维权限。

控制操作持久化为异步回执：accepted → running → succeeded/failed/unknown；HTTP 受理成功不代表服务已启动。一个 runtime 同时只处理一个控制操作，重复请求查询原回执。控制器重启后先核对实际服务及运行证据，不重放不确定的 start/restart。

- **启动/继续**：先核对组织暂停意图、未知记录、预算及配置版本，再按有效运行授权启动。安装/启动进程本身不隐式撤销组织暂停；需要继续派发时走明确的 AU 运行操作。
- **暂停派发**：复用现有持久暂停意图，不要求夺取正在执行者的锁；本轮结束后停止新派发。沿用现有服务对 paused 的退出行为并如实展示服务状态，不保证暂停后进程仍驻留。
- **优雅停止**：停止新派发，等待已发起模型/工具结果及检查点持久化，再确认服务退出。等待窗口依据配置的请求超时、工具上限和持久化余量计算，不机械复用200秒去截断允许600秒的请求。
- **重启**：由同一回执串联优雅停止和重新核验后的启动；无法确认旧执行结果时记 unknown，阻断自动续跑，不以强杀后重启冒充恢复。
- **抢占防护**：网页有限作业、CLI 和独立服务继续共享组织级互斥。托管模式网页运行操作交给控制器，不再另开 Console 线程；已有活跃嵌入式作业需先完成/停止，才能切换模式。
- **续跑边界**：同一任务/任职/章程/连接/工作区版本继续既有会话；版本变化复用现有新会话规则。运行窗口重启不增加原组织累计额度，费用未知不得改成0。

受控实现可用独立进程和 service adapter 替身验证，不依赖真实模型。对 systemd 的实际启停和主机访问必须在 U-008 留下真实证据；替身不构成上线。

## 7. 明确后置

本批不更换 Harness、不引入 Kubernetes/Redis/消息队列，不把 SQLite 共享到多机；不实现同 Agent 跨 AU 任职、成员级独立服务器、浏览器账号托管、任意远程 shell、自动采购/续费、跨主机迁移或无人值守升级。个人长期记忆、专属工作区和模型分配可以扩展，但须各有真实需求和权限设计。

本计划只安排工程工作，不改变原公司章程/预算，不启用真实模型或部署服务，不关闭 New API 的浏览器与真实实例验收阻塞。
