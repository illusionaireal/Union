# U-023 兼容实施与恢复方案

此方案为待实施输入，不表示本轮已迁移。

## 不改什么

- 保留现有组织 ID、state JSON 主结构、成员本地 ID、工作/成果/回执标识与 SQLite 文件布局。
- 既有 board_name/hash/salt、Console 会话和有效版本继续鉴权；不重新生成 Key 或扩大权限。
- 不重写旧 run.package、历史决定或模型检查点，避免回放、哈希和版本失效。
- 不因描述治理主体就改变旧 bootstrap/active、暂停或资源状态。

## 最小实施顺序

1. 实现无副作用的兼容读取投影函数；无新增描述时按旧 meta 和组织 ID 推导 `legacy-board:<au_id>`。只读访问不触发数据升级。
2. 如确需持久治理描述，在当前 AU 的 meta 增加一个带版本 JSON 键（例如 `au_descriptor_v1`）；不新建组织，不移动 DB。写入必须走受信事务、当前版本检查与稳定命令回执。
3. 新创建请求可传入可选主体描述；旧请求保持原字节含义。创建请求重复而内容改变应拒绝，不能借同一请求替换主体。旧客户端无新字段继续运行。
4. 需要给既有组织补描述时，使用单独受信命令，记录旧值、采用时间、操作者和理由，更新状态版本及可审查事件。它仅是描述，不实现控制主体切换。
5. 在新临时组织验证旧记录读取、两种场景创建、兼任/跨 AU 边界、描述写入失败和重启，依已有规则复核权限后才采用。
6. 有实际旧组织迁移需求时，先在暂停/无未决外部执行条件下保存受控一致性备份，再执行显式命令。不批量改生产/私有组织。

## 兼容与恢复

- 回退到旧程序应能忽略新增 meta 键；已写下的事件和历史保留，不能删除回执伪造未执行。
- 写入失败由本地事务回滚；对客户端结果未知时查原命令回执，不重发不同内容的命令。
- 若未来需要真正改变治理主体或跨存储转移，另立协议，不通过修改这个描述键达到权限转移。
- 验收还应验证“只读投影前后 DB 状态版本与预算相同”，避免读取产生静默迁移。
