1. 根[AGENTS.md](../../AGENTS.md)、[HANDOFF.md](../../HANDOFF.md)本次条目及[本轮证据](../../evidence/053-rewrite-checkpoint/README.md)。
2. [PRD](../../docs/PRD.md)：重点是来源、F/P需求、N要求和Q未决项。
3. [总体架构](../../docs/ARCHITECTURE.md)、[ADR-0004](../../docs/decisions/0004-rewrite-delivery-contract.md)、[ADR-0005](../../docs/decisions/0005-au-runtime-boundaries.md)、[ADR-0006](../../docs/decisions/0006-charter-policy-adoption.md)。
4. [tasks.md](tasks.md)及所选切片的既有规格、代码和证据；不要从所有历史文件中的“下一步”随机选任务。
5. [管理方法](../../management/README.md)、当前TASKS及实际Git状态。PRD的原文快照仅供核对历史，不是第二份当前基线。

## 3. 第一项工作：S00 / U-065

接手者先核对实际分支/HEAD、主账、已有工作和当前在制上限。用户此次要求的推送目标是`rewrite/charter-v1`；`dev`仍是日常主线，本检查点不自动合并到dev。

S00的产出是评审后的PRD及ADR状态，以及S01最小精确契约：

- 核实PRD Q-01；如果没有新的材料，就继续使用已列明来源，不另造一个“Charter文件”当作权威。不能把未得到答复写成已确认。
- 对照现有创建/命令/回执路径，确定S01的输入、输出、校验顺序、错误码、事务和读取兼容；记录具体函数落点和相关测试。
- 创建目前跨工作台目录账、AU数据库、凭据文件和资产目录分步持久化；S01契约应明确各步失败后的恢复顺序及原回执查询，保留`test_creation_registration_failure_keeps_unknown_receipt_queryable`等已有保护，不把它们描述成一个跨库/文件事务。
- 对ADR-0005/0006分别给出采用、修改或暂缓结论。产品行为/治理语义有新取舍时提交给产品负责人；既定行为内的工程细节由工程负责人选定并记录。
- 将每条首片需求对应到正常、越权、重复ID、版本冲突、写入中断和重启后的可观察结果；以有意义的行为测试确定RED。
- 开工前补齐所选切片必要的局部AGENTS，注明输入/输出契约、依赖方向和验证；不批量创建未使用的目录或指引。

**S00完成条件**：首片没有会改变行为或数据兼容的未决问题，ADR有明确处置，首片范围和验收已稳定，当前主账可认领。材料不满足时保留具体缺口，不直接编写领域/存储空壳。

## 4. 垂直交付顺序

先完成一个稳定入口和身份/状态用例，再把真实模型、筹建、成果和反馈串起来；随后验证治理调整、持续运行和发布恢复。每片都覆盖其必要界面、API、应用、持久化与测试，保留真实验收的独立条件。

| 阶段 | 切片 | 出口 |
| --- | --- | --- |
| 依据定稿 | S00 | 产品/架构处置和S01精确契约，获得可实施的第一片 |
| 进入系统 | S01 | 普通用户创建并重新打开同一AU，身份/回执/规则不丢失 |
| 真实工作链 | S02 → S03 → S04 | 采用有效模型，真实形成团队、交付成果、反馈后继续；受控工程和真实出口分开 |
| 组织连续性 | S05、S06 | 修章/交接、暂停/等待/重启/未知结果有一致语义 |
| 改进与可维护交付 | S07、S08 | 自主改进有实证，指定环境中安装/升级/回滚/恢复和持续运行可验 |
| 已承诺接入覆盖 | S09 | 按profile逐一交付原生协议/授权/真实工具往返，保留未验项 |

S09可在模型契约稳定后按独立profile推进，每个profile仍是完整用户链；不能把S02的一个成功样本当作全部接入已完成。F21/F22继续依既有后续U卡，不挤入当前首个闭环。

## 5. TDD、协作与切换规则

**TDD Route: strict。依据：2026-11-04用户明确要求。** Aegis用户级默认模式即使为off也不撤销本项目请求。行为代码先RED，最小GREEN，再REFACTOR；纯文档、生成视图和只读核查使用相应结构/一致性检查。

RED必须来自验收行为或真实缺陷：先观察它因缺少/错误行为失败，再实现。既有实现已经满足的要求先保留有效回归；重构用现有测试保护行为，有新边界/不变量才新增对应失败检查，不能故意破坏正确代码制造RED。测试范围包含生产者/消费者、持久化/重启、身份/版本/迟到及实际UI边界。

每片结束重新检查需求映射、架构所有者、兼容/退役和验收范围。权限/资金实现按既有规则独立工程复核；真实Agent测试单独用已授权资源运行，保留所有尝试、未知费用与人工介入。

在契约固定和写入文件范围明确后，可把互不冲突的实现与验证工作交给开发子代理；协调者负责集成、主账和提交。共享事务、同一Schema或同一文件的改动按顺序处理。开发子代理与产品中的AU成员不是同一身份，也不代表组织已经自主开发。

不另建新仓库或手工worktree作为重写前提。保留当前React工作区及现有工程；每片切换前明确旧调用者、唯一写入者、回退方式及旧路径退役条件，禁止永久双写或无证据fallback。

## 6. 命令与证据

从项目根目录使用`.nvmrc`指定的Node 24.19.0及安装好锁定依赖的Python 3.11+环境：

```sh
git status --short --branch
git log -3 --oneline
npm run management:status
npm run check
python3 -m unittest discover -v
```

Windows使用项目`.venv\Scripts\python.exe -m unittest discover -v`；设置`PYTHONUTF8=1`与`PYTHONIOENCODING=utf-8`后运行，避免已记录的本地编码差异。不要把某台机器私有工具绝对路径写入仓库指令。

涉及工作台完整流程时另跑`npm run test:workspace`；模型采用用`npm run test:model-access`及`npm run test:model-service-browser`，其环境条件见现有说明；模型服务用`npm run test:model-service`，发布用`python3 -m unittest tests.test_release_package -v`。这些命令中的本地替身/实际浏览器均不能代替真实供应商、真实容器和运行窗口验收。

新公开证据用新的目录，只保存脱敏结果与范围。私有数据库、认证、宿主配置及原始执行日志留在本机，不提交整个`.union/`。本轮事实和剩余限制见[053证据](../../evidence/053-rewrite-checkpoint/README.md)。
