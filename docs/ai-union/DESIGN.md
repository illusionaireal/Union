## 2026-10-20：已确认的作用和边界

**ai-union** 是以 AI 为核心、围绕共同目标自主组织和持续行动的协作集体，能够自行调整成员、岗位、流程与能力，并对成果负责。

**ai-union-platform** 为这些组织提供创建、托管、观察、接入等公共服务，提供运行条件，不预设组织的业务、结构和经营方式。

**边界是：平台提供服务，组织依据章程、授权与资源自主决定如何发展和完成目标；平台自身也可以由一个 ai-union 建设和运营。**

以上三句话为用户本次确认的产品定义；“UNION 平台”与 ai-union-platform 指同一项目。下文保留此前的产品决定、阶段范围和工程建议；与本节冲突时以本节为准。自组织涵盖运行中的持续调整，不限于初始化。业务能力按组织目标形成，代码开发能力不是所有组织的共同前置条件。组织运行系统是支撑 ai-union 的技术实现，平台可以提供托管等服务；本定义不额外规定组织必须脱离平台运行，或所有能力必须经过平台。

产品定义不代表能力已实现或通过验收；当前实现、真实试跑结果及缺口见[当前状态](STATUS.md)。

## 1. 项目主线

**用户给出目标，ai-union 围绕目标自行形成组织、开展行动，并根据结果持续调整。**

首版输入采用发起人给出的原句：

> 一个持续经营线上内容品牌的 AI 内容工作室。

成员执行循环复用现有 Agent；本项目的设计重点放在组织层循环及其持续状态。

用户不需要预先指定受众、选题、岗位、成员数量、组织层级、制作流程或发布渠道。这些由 ai-union 在可用资源范围内研究、选择、执行和修订。

首阶段以商业组织作为开发和验证对象，首个实例为线上内容工作室。ai-union 的一般定义仍可涵盖学校、研究团队、社会团体等；当前不要求同时实现这些组织类型。

本版替代 v0.2 中“持续维护小软件产品”的首版建议，并撤回由产品设计者预先规定内容岗位、栏目和制作流程的方向。

## 2. 已明确的定义与项目边界

### 2.1 工作定义

union 是两个及以上成员为实现共同目标组成的协作集体，具备成员、目标、结构和管理流程。

**ai-union 是以 AI 为核心，由两个及以上成员为实现共同目标组成，具备成员、目标、结构和管理流程的协作集体。**

human-free 是描述性特征。人类参与不导致其失去 ai-union 身份，也不直接导致体验或测试失败；无需设置资格认证或比例阈值。

本次产品方向进一步要求：成员配置、工作目标的细化、协作结构和管理流程能够围绕输入目标形成，并在运行中调整。这是首版要验证的产品能力，不是给其他组织附加身份判断。

### 2.2 两个项目

| 项目 | 核心任务 | 当前推进位置 |
| --- | --- | --- |
| ai-union | 让一个集体从目标出发形成组织、协作行动、持续调整 | 优先完成定义、首版体验，再推导最小架构 |
| UNION 平台 | 为 ai-union 提供创建、托管、观察、接入与其他服务 | 保留独立规划，按 ai-union 的实际需求承接 |

UNION 平台自身也可以用 ai-union 的方式建设和运营，并设置技术委员会。委员会的建议职责是共同技术规则、关键技术分歧与重要变更审阅；成员可以由 AI、人或两者共同组成。

技术委员会属于平台组织的安排，不预先植入每一个 ai-union。内容工作室是否需要编辑委员会、负责人或其他决策结构，由其自行形成。

项目边界的拆分不等于立即迁移仓库或建设两套基础设施。

### 2.3 Grilling 已确认的产品决定

本节记录发起人对 Q1—Q11 的回答，以及“治理边界属于章程，可通过董事会变更”的补充。它们作为当前产品设计依据。后文的具体数据结构、调度和存储方案仍为实现建议，不因本轮确认而全部视为已冻结。

| 事项 | 已确认决定 |
| --- | --- |
| 治理主体 | 董事会保留最终控制权。首版由发起人代表董事会，AI 提供经营报告、建议和议案 |
| 首阶段组织类型 | 先以商业组织开展，便于观察价值、投入和经营结果；首个实例为线上内容品牌 |
| 长期商业目标 | 盈利或至少覆盖各类费用实现自维持，包括 token 等模型费用；在资金耗尽前取得下一笔投入也是继续经营的途径。经营收入与融资分开记录 |
| 首版成功标准 | 自行形成组织、真实对外交付、可核验外部反馈，以及据此完成下一轮决定和行动；收入、增长和盈利先作为观察结果 |
| 岗位驱动 | 岗位决定职责、权限和所需上下文；组织或任务持有正式知识与成果，岗位履职记录可交接 |
| 成员与岗位 | 一名成员可以兼任多个岗位，同类岗位可有多个席位；每项工作明确负责岗位及任职成员。执行器和运行会话不等同于成员 |
| 自组织范围 | 经营层可在授权内调整策略、岗位、人员、协作与受支持的内部规则。新增执行能力、修改核心运行程序列为后续能力 |
| 治理边界 | 由章程规定，董事会可以通过修章变更。经营层不能自行修改董事会席位或最终控制权 |
| 日常对外行动 | 在董事会已授权的账号、渠道和额度内自主行动，无需每篇内容都由人批准。新增权限、超额支出、融资或签约等按董事会保留权处理 |
| 经营失败与停止 | 组织可主动提出转向、缩减、暂停或追加投入。原额度耗尽后暂停；新的投入、根本方向变化及最终解散按章程由董事会决定 |

当前关于对外行动的确认属于产品行为与授权机制设计。具体账号、渠道、预算、期限和实际服务接入在实施时配置；本文件没有替代这些实际授权。

human-free 继续作为描述性特征，不设置零人工或比例门槛。

### 2.4 章程在架构中的位置

**组织运行章程是治理边界的正式依据。董事会按现行章程修订它；经营层依据生效章程自主组织和经营；运行程序负责按生效规则执行。**

建议采用以下关系：

| 层次 | 内容及关系 |
| --- | --- |
| 章程 | 组织宗旨、董事会设置与保留权、经营授权、资源与风险边界、修订和生效程序 |
| 董事会决定 | 依章程作出的投入、根本方向、任命、修章、暂停或解散等决定 |
| 经营制度与岗位授权 | 经营层在章程和董事会授权内形成的内部决策方式、岗位、任职及工作流程 |
| 运行状态与执行 | 保存当前生效版本、授权投影和工作状态，派发允许的行动并记录结果 |

初始董事会保留事项包括：组织宗旨和根本目标、投入与风险边界、董事会自身规则、增资或融资授权、最终解散。它们是本轮同意的初始安排；治理边界的后续变化由董事会通过章程程序处理，不固化为不可修订的业务代码。

经营层可提出修章议案，说明原因、影响与预期效果。议案在生效前不扩大经营层权限。章程变化本身也不自动创建外部账号权限或尚未实现的执行能力。

首版可采用“章程正文及结构化可执行条款组成同一版本”的表示方式。组织状态引用生效版本；数据库中的权限和路由是该版本的运行投影，不另立一套可独立修改的治理事实。涉及判断性的条款保留解释与决策依据；正文与执行字段有冲突时，明确反馈并修订，不能由执行层静默扩大授权。

程序可以固定版本管理、决议记录、权限检查与状态提交机制；具体董事会保留事项、经营层授权和额度值从生效章程与决定读取。

### 2.5 章程修订与生效（实现建议）

1. **提出修订**：保存拟修改条款、理由、影响以及希望何时生效。
2. **形成董事会决定**：按当前生效章程确认有权参与决定的董事会及修订程序。首版由发起人代表董事会。
3. **保存新版本**：记录董事会决定、章程正文及执行条款、版本和生效安排。
4. **切换运行依据**：更新当前生效引用和相应授权，向受影响岗位及任务发送变更事件。
5. **处理在途工作**：明确哪些工作继续、取消、缩减或交接；新行动依据当时生效授权，历史行动保留其原依据和实际结果。

新规则不追溯性地授权自己的修订。修改章程可以改变后续治理安排；它不会改写已经发生的事实，也不能仅凭版本切换撤回已经完成的外部动作。

初始章程可以由通用模板生成并由董事会采用；其中预置治理与运行边界，不预置具体经营岗位、内容栏目或业务生产流程。具体章程表示、修订接口及一致性实现仍待工程设计。


## 3. 首版需要提供什么、让组织决定什么

| 来源 | 提供或形成的内容 |
| --- | --- |
| 发起人／董事会 | 输入初始目标并采用组织运行章程；在章程程序下确认根本方向、投入、治理边界及其变更 |
| 运行环境 | 已配置的模型、工具、存储、资源额度、可执行动作及账号权限 |
| ai-union 经营层 | 在生效章程与授权范围内形成目标解释、阶段目标、经营策略、岗位、任职、工作安排及组织调整 |

目标中未明确的事项，可以先形成假设，记录依据并通过行动验证。系统不应把所有经营选择退回给用户填写。

章程模板与已有资源配置可以复用，因此体验上仍可从一句目标启动；相应的章程采用、董事会身份和授权范围需形成明确记录。不存在的账号、工具或权限应如实反映，章程授权本身不能替代外部服务的实际接入。

首版需要有一个通用的启动过程，让模型开始理解目标并建立最初组织。启动过程可以规定可用操作和资源边界；内容行业的角色表、成员数量、层级与生产步骤不应写死在启动逻辑中。启动者是否继续担任管理角色，也是后续组织能够调整的事项。

“自组织”的证据必须同时包含决定与执行：新增成员后该成员实际工作，调整职责后后续执行随之变化，新的决策结构能够实际影响任务安排。只生成组织介绍或角色对话不足以证明这项能力。

## 4. 首版体验草案

下表描述用户能够观察到的状态，不强制组织采用对应的固定工作阶段。

| 用户看到什么 | 系统应做到什么 | 留下的证据 |
| --- | --- | --- |
| 输入目标，开始运行 | 理解目标和资源条件，提出初始解释与阶段目标 | 原始目标、假设、阶段目标及依据 |
| 组织逐渐形成 | 自行确定所需成员和职责，形成协作与决策关系 | 实际成员身份、职责、结构及建立原因 |
| 组织开始行动 | 成员依据自身责任执行，相互交换资料、成果和决定 | 行动、任务依赖、产物与决策记录 |
| 出现首批成果 | 根据自行确定的策略产出可检查、可发布的实际内容 | 内容文件、必要来源或素材记录、发布状态 |
| 反馈影响后续工作 | 理解反馈或环境变化，选择继续、修正或调整组织 | 前后变化、理由、下一轮行动与成果 |

用户应能随时看懂：目标是什么、组织如何组成、现在在做什么、已经产出什么、接下来准备做什么。具体内容可以包括文本、音频、视频、直播内容或短帖；实际选择取决于组织策略和可用工具。

这些视图从运行记录生成。界面不得把预写的成员、事件或示例成果冒充实际运行。

### 第一里程碑

**输入上述一句目标并具备董事会授权的有限资源后，系统自行形成组织，完成一次真实对外交付，取得可核验的外部反馈，再完成下一轮经营决定和实际行动。**

需要能够核对：

- 组织中的至少两个成员确实执行了工作，成员之间有成果或决策依赖。
- 策略、岗位、成员数量和流程来自本次运行，能够追溯其形成依据。
- 产物可以打开、阅读、收听或观看，不能只给出计划或“已经完成”的文字声明。
- 反馈实际影响了后续判断或行动。反馈不一定要求改组；合理保持原结构也可以。
- 任务跨轮继续，已有决定、成果、责任和进度能够保留。
- 失败、受阻和人工参与如实记录。

开发阶段可以使用试验环境。首版验收应覆盖上述真实交付与反馈闭环；可发布文件、试验发布和实际对外交付分别记录。没有反馈时如实报告并处理，不用模拟反馈或内部成员评价代替市场反馈。收入、增长和盈利先作观察结果，不是首版通过门槛。具体试验窗口、预算和渠道在实施时配置。

## 5. 组织 loop 首版设计（实现建议）

本节为针对 ai-union 的设计建议，尚未实现或通过测试。成员执行循环复用现有 Agent；本项目重点实现组织决策与状态变化，以及到执行层的适配。

### 5.1 运行单位与基本循环

每轮处理一个组织问题，或一组彼此相关的问题。轮次由事件或预定复盘触发，使用有限资源执行后交付决定、继续跟踪或进入等待。

**接收变化 → 找出目标差距 → 依据当前规则形成决定 → 落实工作或组织变更 → 执行与收集结果 → 更新事实并触发后续判断。**

策略判断由 AI 完成；状态提交、责任路由、任务派发和唤醒由程序执行。一次组织循环可以调用一个或多个现有 Agent；它不对应固定的公司岗位。

成员职责范围内的日常执行继续交给执行层。只有新的目标差距、跨成员依赖、资源冲突、阻塞、策略失效或预定复盘等问题进入组织决策。

### 5.2 最小组织状态

| 对象 | 最少内容 | 作用 |
| --- | --- | --- |
| 目标 Goal | 初始委托、当前经授权的组织目标、阶段目标、预期成果与观察依据 | 保留目标演变，经营层不能自行降低外部验收标准宣称成功 |
| 章程 Charter | 正文、生效版本、董事会保留权、经营授权、修订程序和生效安排 | 作为组织治理边界的正式依据 |
| 岗位 Role／Position | 职责、能力需求、权限与上下文范围、具体席位 | 由岗位驱动责任和信息访问 |
| 任职 Assignment | 成员与岗位的关联、有效范围和任职期间 | 支持兼岗、多个席位及责任交接 |
| 成员 Member | 稳定身份、能力、任职关联、执行器绑定、可用状态 | 职责和授权由当前岗位及任职关系确定；更换执行器不自动新增成员 |
| 工作 Work | 目标关联、负责岗位及任职成员、输入、交付物、依赖、期限或复查时间、状态 | 跟踪责任、承诺和工作衔接 |
| 规则 Policy | 决策范围、决定者、需咨询者、异议处理、替补或超时安排、版本 | 决定谁能对什么作出决定以及如何生效 |
| 证据 Evidence | 成果引用、工具回执、外部反馈、来源、时间、确认程度 | 区分“有人报告完成”与已经观察到的结果 |
| 决定 Decision | 问题、依据、决定者、所用规则版本、变更、责任和复查条件 | 让决定产生执行效果，并支持事后检查 |
| 运行条件 Runtime | 可用工具、资源额度、已使用资源、事件游标、待唤醒项 | 在实际资源内运行，停止空转并支持延续 |

这些是逻辑对象，可以先保存在一个数据库中。成员消息可以保存，但消息记录不替代正式的任务、决定和成果状态。组织摘要用于装载上下文，原始证据与历史记录保留可查询引用。

根本目标、治理边界和经营授权依据生效章程及董事会决定。经营层可以在授权范围内修改阶段目标、岗位、分工和管理方式；需要扩大授权时向董事会提出变更。章程中的治理边界可由董事会按现行程序修订，不硬编码为永久不可变的业务规则。初始目标及历史授权仍保留记录。

### 5.3 触发方式与问题识别

首版支持以下事件：

- 目标建立、董事会目标变更或章程新版本生效。
- 成员交付、执行失败、请求协助或报告阻塞。
- 外部反馈或新的相关证据到达。
- 成员可用性、工具或资源条件发生变化。
- 已安排的工作到期、复查到期或战略复盘时间到达。

事件首先保存，再作去重与合并。可以直接确定的变化（例如任务超时）由程序登记；机会价值、目标差距和策略是否失效由 AI 判断。大文件和完整会话按需读取，不把所有成员历史塞进一次模型调用。

初始任务完成后，根据目标性质安排下一批工作或未来复盘。组织可以调整复盘节奏，并在持续无进展或目标不可达时提出转向、缩减、暂停或追加投入建议。原额度耗尽后进入暂停，保留原因和恢复条件；新的投入、根本方向变化及最终解散按章程由董事会决定。无可执行工作时等待，登记事件条件或下一次检查时间。

### 5.4 谁形成决定：规则与执行器分离

组织决策先依据生效章程区分董事会保留事项与经营层授权事项。首版由发起人代表董事会，AI 提供报告和议案。经营层可采用“按范围指定决策责任人，允许相关成员提出异议”的初始机制；这一具体机制仍为实现建议。授权范围内的日常经营和对外行动自主执行，无需逐项人工批准。

规则需要能回答四个问题：

1. 当前问题归谁决定？
2. 哪些受影响成员需要提供事实或意见？
3. 有异议、无人响应或决定者不可用时怎么继续？
4. 谁按现行规则有权修改这条规则？

程序根据已生效的规则找到负责人；负责人调用现有 Agent 收集必要信息、形成判断。决定可以保留异议，不能把没有回复算成赞成。未满足规则规定的条件时，记录等待或按现有替补、超时规则处理。

首版先支持负责人决定与有限咨询。后续可扩展共识或投票等决策机制；模型提出当前运行环境不能执行的新规则时，作为未支持的提议保留，不宣称已经生效。

规则变更依据当前生效章程及其授权处理。董事会可以按章程程序修订治理边界；经营层可以在授权内变更内部规则。新规则不用于追溯性地授权自身。经营层不能自行修改董事会席位或最终控制权。

### 5.5 从空白启动

1. 保存初始目标、董事会已采用的章程版本及已有运行条件，建立初始组织状态。
2. 唤醒一个通用启动 Agent。它在章程授予的临时权限内输出阶段目标、岗位与成员任职、内部决策规则和首批工作。
3. 将符合运行条件的方案写入组织状态，并派发首批工作。无法执行的部分返回具体原因供修订。
4. 启动权限在完成首次组织建立后结束；之后按已经形成的规则运行。启动者若继续承担职责，需要出现在正式成员和规则中。

不预装行业岗位。正式形成的 union 需有至少两个可区分的成员，这是已确认定义；具体数量及职责由组织确定。一个模型可支持多个成员，但任务责任、相关上下文与成果归属需要可区分。

启动 Agent 的作用是建立最初安排。首版对它提出的初始安排没有“最优组织”的保证；组织在后续结果中修订这些安排才是要验证的能力。

### 5.6 决策输出必须可以执行

一个组织决定采用结构化输出，至少包含：

- issue：此次解决的问题与关联目标。
- evidence_refs：用于判断的事实与成果引用；缺失证据需注明。
- decided_by / charter_version / policy_version：决定者、所依据的生效章程及适用内部规则版本。
- operations：新增、修改或停止哪些工作；怎样调整成员、职责或规则。
- expected_effect：预期缩小什么差距，如何观察。
- review_trigger：哪项交付、外部信号或哪个时间点触发复查。
- outcome：落实变更、保持现状、补充调查或等待；相应理由与后续条件。

这些字段是执行与追踪协议，不规定内容行业的业务流程。决定可以很小，只分配一项工作；也可以修改协作结构。每轮不要求改组、不要求新增成员，也不强制生成多个方案。

程序检查对象引用、生效章程及适用规则、权限、资源条件与状态版本，并将已采用的决定和组织状态一起提交。程序无法仅凭结构化字段保证商业判断正确；结果质量仍需来自成果检查和实际反馈。

首版让同一组织的状态变更串行提交，成员执行可并行。基于过期状态作出的冲突决定返回重新判断。决定中的新任务先持久记录再派发，防止组织状态已经更新却没有实际启动工作。

这是小范围的一致性设计，不要求先建立完整分布式事务系统。任务派发用稳定工作 ID；外部执行器的去重和恢复能力按实际接口处理，不能据此宣称外部动作绝不会重复。

### 5.7 运行中的调整与责任交接

组织可以执行以下种类的变化：

| 类别 | 可实施动作 |
| --- | --- |
| 工作 | 建立、分配、修改、取消工作，调整优先级或依赖 |
| 成员 | 创建、暂停、替换或退出成员 |
| 协作 | 调整职责、责任人、资源与协作关系 |
| 规则 | 在章程授权内修改内部决策责任、咨询范围、异议处理或复查节奏；治理边界修订进入董事会流程 |
| 方向 | 依据董事会授权的组织目标修订阶段目标和策略；根本方向变化按章程决定 |

对正在执行的工作，变更必须说明继续、取消或交接。移除成员前处理其未完成责任；历史成果不删除。原执行器迟到的结果保留并标明其对应的旧任务版本，不自动覆盖新的正式结果。

不是所有“新方法”都要求改核心代码。首版优先让组织通过现有成员、任务和规则组合形成方法；新增工具或改写运行程序属于额外能力范围，需要明确支持情况。

### 5.8 执行层适配

组织层向现有 Agent 发出一个工作包：

- 工作 ID、负责岗位、任职成员、当前任务及适用章程版本。
- 目标、相关上下文与资料引用。
- 预期交付物及观察条件。
- 可用工具和资源范围。
- 结果返回位置和需要通知的对象。

执行层返回：已接收、进行中、交付、阻塞或失败，以及产物和依据。首版适配器至少实现提交、状态查询、结果接收；取消、会话恢复和进度推送按执行器能力声明，不假设所有 Agent 已具有相同接口。

成员不必全部使用同一产品或模型。更换执行器时，组织中的责任与工作记录仍然存在。对外发布等动作是否真正执行，以工具回执和可核验结果为准。

### 5.9 一次循环的抽象流程

```text
收到事件，并保存实际发生的变化
    找到生效章程、相关目标、未完成工作、内部规则与证据
    确定是否需要组织决策，合并相关问题
    区分董事会保留事项与经营层授权事项，找到决策责任人
    使用现有 Agent 形成决定；必要时咨询受影响成员
    检查决定是否可以按现行规则和资源条件落实
    保存决定、组织变更、待派发工作与复查条件
    派发工作；等待执行结果或下一次触发
执行结果进入新的事件，继续上述过程
```

这里没有固定的内容生产流程，也没有要求所有成员按同一时钟开会。组织判断、成员执行和外部环境按各自节奏推进。

### 5.10 基本架构与最小实现顺序

逻辑模块为：

| 模块 | 职责 |
| --- | --- |
| 状态与记录 | 保存组织当前状态、事件、决定和成果引用 |
| 上下文与资料 | 按任务组装上下文，检索版本化文档，记录带来源的记忆 |
| 组织循环执行器 | 汇总变化、装载相关上下文、调用决策责任人、落实决定 |
| 调度 | 工作派发、结果接收、定时复查和等待唤醒 |
| Agent 适配 | 对接已有执行 Agent，统一任务与结果协议 |
| 观察界面 | 展示目标、成员、责任、当前工作、成果和组织变更 |

首版可放在单个应用中，复用现有模型调用和 Agent 运行能力。逻辑模块不等同于必须部署的独立服务。状态存储应能跨进程重启保存；具体库和部署位置留给工程选型。

开发顺序建议：

1. 实现组织状态、启动事件与结构化决定；先用一个真实 Agent 产生初始组织。
2. 接入现有执行 Agent，让决定真正派发工作并获得实际成果。
3. 接回交付、阻塞与外部反馈事件，完成第二轮组织决定。
4. 实现职责调整、规则更新和责任交接，证明变更能够影响后续执行。
5. 加入等待唤醒与最小恢复能力，再检查持续运行表现。

代码可分步实现；首个完整演示应覆盖上述闭环，不能将组织图生成当作已经实现 ai-union。

### 5.11 三个聚焦的验证问题

- **形成与落实**：同一个原始目标下，运行产生的组织配置是否被实际执行，成员是否形成协作和可检查成果？
- **调整与连续性**：当依赖受阻、成员不可用或反馈改变时，组织能否保持责任连续并作出有效调整？保持现状也可能是合理决定。
- **长期运行**：一次任务结束或进程恢复后，未完成承诺和复查安排是否仍在，能否继续推进而不是丢失目标或空转？

内容质量和真实经营效果仍单独评估。组织内部自评不能代替外部证据。human-free 继续仅作描述。


## 6. 上下文、记忆与文档设计（实现建议）

本节沿用“成员执行层复用现有 Agent”的边界。组织层负责跨成员、跨会话的共同信息，执行 Agent 内部的上下文压缩和私有运行机制可以复用。

### 6.1 四种不同职责

| 概念 | 保存或呈现什么 | 更新方式 |
| --- | --- | --- |
| 组织状态 | 当前生效的目标、职责、任务、规则与资源安排 | 通过有记录的组织决定和实际执行事件更新 |
| 长期记忆 | 过去发生的事情、已有知识、经验、假设与适用条件 | 依据来源写入，必要时更正、合并、标记争议或失效 |
| 文档与资产 | 原始资料、研究、方案、成果，以及文本、音频、视频等内容 | 保存稳定身份和具体版本；保留来源与衍生关系 |
| 本次上下文 | 某个成员或决策过程此刻实际需要读取的信息 | 根据目标、职责、问题和可用上下文空间临时组装 |

四者是职责划分，不要求部署四套服务。文档可以承载记忆正文；长期记忆可保存摘要、出处及适用条件。上下文是从上述信息中选取的运行视图。

组织状态记录“当前采用什么安排”。它不意味着组织对外部世界的判断必然正确。对外部事实，仍需保存来源和不确定性。

同一规则不维护两份可独立修改的正式正文。短规则可直接结构化保存；长篇规则正文存为文档，由组织状态引用当前生效的具体版本。修改草稿不会自动改变生效规则。

### 6.2 信息归属与岗位访问

- **组织范围**：共同目标、生效规则、正式决定、共享事实与组织级经验。
- **工作范围**：某项任务或项目的资料、草稿、协作讨论和未解决问题。
- **岗位履职记录**：由组织持有，保存任职所需的责任、决定和交接信息；岗位决定可访问的资料及上下文范围。
- **成员范围**：成员的工作笔记、局部假设、执行进度和个人经验；组织正式知识和成果不随成员离任而丢失。

组织共有的信息可以被相关成员检索；它不需要默认进入所有成员每次调用的上下文。成员可以直接写自己的笔记，并提交带署名和来源的共享观察；个人判断不会自动变成全组织已确认事实。

成员记录绑定组织内稳定的成员身份，不绑定某个供应商会话。更换执行器时，组织可以重新装载必要工作记录。工具或 Agent 产品的本地记忆可作为补充，不能成为组织目标和责任的唯一存放处。

所有检索先限定组织、访问范围和任务关系，再匹配内容。公开资料、组织指令和成员笔记保持类型标记；资料中的文字不自动获得修改组织规则的效力。

### 6.3 如何组装每次上下文

唤醒一个成员或决策过程时，按以下顺序准备信息：

1. **当前任务所必需的组织信息**：当前授权目标、相关阶段目标、岗位职责及任职关系、生效章程中的适用条款和内部规则。
2. **当前工作状态**：此次问题、未完成责任、依赖、已形成决定、当前阻塞和预期结果。
3. **增量变化**：自上次处理以来与当前问题有关的事件、成果和反馈。
4. **相关知识与证据**：按来源、适用范围和有效状态挑选的记忆摘要、文档片段与版本引用。
5. **继续读取的入口**：成员可按 ID、关键词、关联任务等继续查询原文或其他资料。

当前授权目标、岗位职责、生效章程及适用规则按确定的关联读取，不依赖语义检索“碰巧找到”。资料探索先使用对象关联、元数据和全文搜索；规模或表达差异确有需要时再增加向量检索。检索索引可以重建，不承载唯一的正式记录。

上下文预算按执行模型和任务配置，不规定所有成员使用同一固定 token 配额。必须保留适用规则、当前问题和未完成责任，并为输出及进一步工具读取预留空间。较长的参考内容优先提供摘要和引用；遇到不足应明确检索，而非凭空补齐。

上下文的简短清单记录：生效章程、岗位及任职、组织状态版本、使用的决定与文档版本、检索或摘要的来源，以及相关限制。这便于事后解释一次判断是基于哪些信息。

组织决策上下文侧重跨成员问题、资源和结果；执行上下文侧重任务细节。二者使用同一套持久记录，不要求获得相同文本。

### 6.4 如何写回记忆

每轮执行或决策结束，分别处理：

| 信息 | 写回处理 |
| --- | --- |
| 实际事件与工具结果 | 记录发生时间、工作 ID、执行者、结果和必要证据引用 |
| 产物与资料 | 保存原件或可用引用，创建文档／资产版本，关联任务与来源 |
| 正式组织决定 | 按第 5 节决策机制提交，更新生效状态及其引用 |
| 可复用经验或知识 | 保存内容、证据、适用条件、记录者和不确定性；注明是观察、假设还是经检查的结论 |
| 执行中的临时记录 | 保留为工作或成员笔记；无复用价值时不推入组织摘要 |

普通笔记和观察可以即时记录，不需要为每条记忆设置管理审批。能够约束他人的新规则、职责或政策，仍应通过组织决策生效。经验变成制度需要明确的采纳决定。

记忆可由正在执行的 Agent 提出，也可在任务完成后整理；首版不要求预设“记忆管理员”岗位。程序自动记录已知的任务和版本信息，AI 负责提出哪些经验值得复用以及怎样概括。

共享知识出现矛盾时，保留各自来源和适用条件，标为待核实或存在分歧。最近写入不自动代表更正确；程序也不能因模型声称“已验证”就给出超出实际证据的确认状态。

摘要和索引是派生内容。关键来源缺失、被替代或过时后，对应摘要应标记需要重新核实或重建。来源失效不必然证明旧结论错误，但必须让后续使用者知道证据条件已改变。

### 6.5 文档、版本与生效关系

每项文档或资产至少具有：

- 稳定 ID、版本、类型、标题或名称。
- 创建者、所属组织／工作／成员及关联任务。
- 正文或资产位置、创建和更新时间。
- 草稿、采用、发布或归档等适用状态。
- 来源、衍生关系及必要的替代关系。

状态名称可以按内容类型配置，首版不把所有文件套入同一审批流程。个人笔记、外部资料、正式决定和公开作品的生命周期不同。

首次记录建立身份，修改形成新版本；并行修改以各自读取的版本为基准，冲突时合并或重新处理，不默默覆盖他人成果。正式成果引用具体版本；公开发布时记录实际发布的版本与渠道回执。

组织状态只指向当前生效的规则或安排版本。检索默认区分当前有效记录、最新草稿和历史记录；找历史时可显式查询。文件更新时间不能代替组织的生效决定。

对音频、视频和图片，原文件是资产；转录、字幕、摘要或缩略图作为关联版本保存。文本索引只帮助定位内容，不替代对原资产的检查；字幕修改也不代表原音频已经修改。

成员可以自行创建、命名和整理工作文档。我们规定稳定身份、版本、引用和基本写入机制；具体文档体系、模板和知识分类可以由组织自行形成。

### 6.6 更新传播、压缩与交接

章程、岗位职责、任职、任务或正式成果更新后，系统向相关工作产生变更事件。新任务装载当前生效版本；正在运行的成员在下一次协作边界处理通知。提交组织变更或执行会受权限变化影响的动作前，再检查相关生效版本，不能仅依赖旧上下文。

无法立即取消的外部执行应显式标记其状态。组织重分工后收到的迟到成果仍绑定原工作版本，经过现行责任人处理后再纳入当前结果。

会话压缩保留当前目标、责任、未完成事项、有效决定、重要分歧及来源引用。可以减少重复工具输出和已解决讨论；关键证据保留在持久记录中。应从正式记录与来源重新生成摘要，避免长期只对上一轮摘要继续摘要。

成员交接至少包含：当前任务、已经作出的决定、成果版本、尚未解决的问题与下一次触发条件。新的执行 Agent 据此继续，并可以检索原始资料；不依赖旧 Agent 对话仍留在上下文中。

数据保留可按类型安排。关键决定和仍被成果引用的证据优先保留；低价值过程日志可以按运行条件归档或清理。清理必须处理相应的引用、摘要和索引，不能留下看似可追溯但已无来源的记忆。

### 6.7 首版技术组织与接口

建议先用以下组合：

| 能力 | 建议的最小实现 |
| --- | --- |
| 组织状态、版本元数据、事件和记忆条目 | 一个持久数据库 |
| 文档正文和多媒体文件 | 文件系统或对象存储，以版本引用 |
| 检索 | 关联查询、元数据过滤和全文搜索 |
| 上下文组装 | 一个可复用的组装模块，生成必要内容与来源清单 |
| Agent 接入 | 统一的任务输入、查询读取和成果回写接口 |

这是逻辑设计；数据库与文档正文可以在小规模时合并存放。向量索引可后加，知识图谱不作为首版前置条件。

组织层最少提供四组操作：

1. 读取当前组织状态，以及检索、读取指定版本的资料。
2. 保存新文档版本或任务成果。
3. 记录带来源、范围和适用条件的记忆／观察。
4. 提交组织决定，按现行规则改变正式状态。

现有 Agent 可以通过工具 API 接入；需要文件操作的 Agent，可获取按版本生成的工作目录和上下文说明。工作目录修改通过回写接口形成新版本，正式状态通过决定接口修改。执行器内部如何压缩对话继续交给其自身机制。

整个信息循环为：**装载当前状态与相关记忆 → 决策／执行 → 保存成果和事实 → 落实决定 → 整理可复用经验 → 更新后续成员需要读取的内容。**

### 6.8 首轮验证重点

- 新会话或更换 Agent 后，能否准确继续未完成责任？
- 规则更新后，新任务是否读取生效版本，旧工作是否收到相关变更？
- 草稿或个人假设是否被误当成正式规则或已确认事实？
- 摘要中的重要判断能否找到来源，并在矛盾或来源过时后反映变化？
- 多成员修改同一资料是否保留版本并处理冲突？
- 发布或交付记录是否指向实际产物版本，包括音视频原件？

本节只提出设计与验证问题，没有执行上述测试或建立存储系统。

### 架构阶段需要解决的最少问题

1. 怎样启动一次组织形成过程，并把形成的成员、责任和规则变成可执行状态？
2. 怎样适配已有 Agent 的任务提交、状态和结果接口，使组织责任与执行会话分离？
3. 目标、成员、任务、决定、成果和反馈怎样跨轮保存？
4. 怎样由时间、任务完成或新反馈触发后续行动，避免每一轮都依赖用户重新发指令？
5. 组织怎样提出并实施自身变化，系统怎样记录变更前后的关系？
6. 用户怎样看清进展并进行必要干预？

这些是待解决的能力问题。具体模型、数据库、编排框架和部署方式在复用评估后选择。先完成一条真实运行过程所需的能力，再由运行中的问题决定扩展优先级。

## 8. 将首版运行转为 bench test

### 8.1 第一轮回答的问题

在给定目标和资源条件下，系统能否形成并实际运行一个有效组织，产出成果，并根据反馈继续推进？

首轮不预设标准组织图、岗位名单或必需的改组次数。不同运行形成不同结构是允许的，重要的是成果、成本及组织选择的实际作用。

### 8.2 可重复的试验条件

使用相同初始目标、工具范围、资料快照和总资源额度。对于变化场景，预先定义统一的触发条件及影响，例如可用工具变化或一组受众反馈；不能因某次运行的结果临时改变测试条件。模拟信息与真实反馈分别标明。

单次运行验证是否跑通；随后做小规模重复运行，保留成功与失败。模型版本、工具、初始条件和人工参与均随结果记录。

### 8.3 结果与组织过程一起看

| 观察对象 | 可检查的证据 |
| --- | --- |
| 成果 | 是否满足预先明确的外部验收标准、完成真实对外交付；另外检查组织自行细化的内容目标 |
| 外部反馈 | 是否有可核验的真实反馈及由此产生的下一轮决定和行动 |
| 内容质量 | 根据实际内容类型检查事实与来源、论证、叙事一致性或视听质量；主观评价与客观检查分别呈现 |
| 组织形成 | 哪些成员和结构由运行产生，分别承担了什么实际工作 |
| 协作与调整 | 信息或成果如何影响其他成员，哪些变更实际改变了后续行动 |
| 持续性 | 能否利用已有成果与反馈继续工作，是否重复犯错或丢失进展 |
| 资源与参与 | 总耗时、模型及其他可核对费用、人类参与方式；经营收支与融资分开记录 |

评价者应在运行组织之外，不能把组织自称完成或内部审阅通过直接等同于外部评测通过。

实际阅读、收听、回访、关注和收入作为真实运营结果观察。模拟测试可验证部分组织能力，不能替代首版的真实对外交付与反馈。长期商业目标是覆盖各类费用并自维持，或在资金耗尽前取得下一笔投入以继续经营；融资续存与经营盈亏平衡分别报告。首版不以收入或盈利作为通过门槛，也不因此将支付模块置于开发首位。

稳定跑通后，可在相同总资源条件下比较单 Agent、预设组织和目标驱动自组织。多成员预算合并计入，避免将更多资源误当成组织机制带来的提升。初期保留各维度结果，不急于合成总分。

human-free 仅描述实际运行特征，不设置通过阈值。
