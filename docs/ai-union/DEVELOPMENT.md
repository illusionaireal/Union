## 1. 项目主线与当前依据

**用户给出目标，ai-union 围绕目标自行形成组织、开展行动，并根据结果持续调整。**

首版目标使用原句：

> 一个持续经营线上内容品牌的 AI 内容工作室。

用户提供目标、采用章程并配置资源。组织自行确定受众、经营策略、岗位、成员数量、协作结构、内容类型与工作流程。具体经营方法不预写进程序或系统提示词。

成员执行循环复用现有 Agent。本项目重点是组织层的持续状态、决策、协作、授权、记忆和反馈循环。

产品基线见 [章程治理与组织架构 v0.6](DESIGN.md)，原文更新时间为 2026-10-10 19:00:51（北京时间）。本文将该基线与随后确认的开发方法整理为可执行交接材料；原文第 5—6 节的具体实现仍属于工程建议。

本文与 [DESIGN.md](DESIGN.md) 是仓库内的产品与开发依据；实现进度见 [STATUS.md](STATUS.md)。用户在新 session 的明确新决定应同步更新 Spec 和决策记录。

### 1.1 已确认的产品决定

| 事项 | 已确认内容 |
| --- | --- |
| ai-union 定义 | 以 AI 为核心，两个及以上成员围绕共同目标组成，具备成员、目标、结构和管理流程的协作集体 |
| human-free | 描述性特征；不设零人工要求、比例门槛或身份认证 |
| 首阶段类型 | 先做商业组织；首个实例是持续经营线上内容品牌的 AI 内容工作室 |
| 长期经营目标 | 盈利或覆盖全部费用实现自维持，包括 token 等成本；下一笔投资可以支持继续经营，融资与经营收入分开记录 |
| 首版验收 | 自行形成组织、真实对外交付、可核验外部反馈，并完成下一轮决定和实际行动；首版不要求盈利 |
| 董事会 | 保留最终控制权；首版由发起人代表董事会，AI 提供报告和议案 |
| 章程 | 治理边界属于章程；董事会按现行章程程序修订，系统按生效版本运行 |
| 初始保留权 | 宗旨与根本目标、投入与风险边界、董事会规则、增资或融资授权、最终解散；后续边界可通过修章变更 |
| 日常自主权 | 在章程及已配置的账号、渠道、预算授权内自主经营，不逐篇要求人工批准；扩大授权、超额支出、融资或签约等按保留权处理 |
| 岗位驱动 | 岗位决定职责、权限和所需上下文；成员可以兼岗，同类岗位可以有多个席位 |
| 成员身份 | 成员具有稳定身份；模型、执行器、会话与成员分离；每项工作明确负责岗位及任职成员 |
| 知识与交接 | 正式知识和成果归组织或任务；岗位履职记录可交接，不随成员离任消失 |
| 自组织范围 | 首版支持策略、岗位、成员、工作和受支持内部规则的调整；新增工具能力、修改核心运行程序属于后续能力 |
| 失败与停止 | 可以提出转向、缩减、暂停、追加投入；原额度耗尽后暂停，新的投入、根本方向与最终解散按章程决定 |
| 项目拆分 | ai-union 与 UNION 平台分别规划；仓库是否拆分由实际工程需要决定 |
| 平台自举 | UNION 平台未来可以用 ai-union 运作，并设置技术委员会；不要求每个 ai-union 都预置技术委员会 |

章程授权与真实服务权限分别处理：章程生效不会自动获得外部账号、工具或资金。

## 2. 开发方式与交付约定

### 2.1 四种方法各自负责什么

| 方法 | 使用位置 | 实施方式 |
| --- | --- | --- |
| 轻量 SPEC | 每个开发迭代 | 写清用户可见行为、边界和验收证据，再形成技术方案及任务；随实际决定维护 |
| TDD | 有明确预期的核心机制 | 先写会因缺失行为而失败的测试，再实现并重构；覆盖重要规则与状态变化 |
| Agent 评测 | 自组织、协作、判断与持续行动 | 真实模型运行，检查实际成果、状态和行动记录；检查有效行为，不锁定唯一措辞或岗位图 |
| 完整闭环迭代 | 开发顺序 | 从目标到行动、成果及后续决定逐步打通，尽早接入真实执行器 |

优先使用 GitHub Spec Kit 承载 Spec → Plan → Tasks → Implement。先核对当前环境的安装与集成方式；若工具不可用或接入会阻塞本轮，可用等价 Markdown 文件完成同样流程，并记录原因。不要将安装工具或迁移全部旧文档单独扩展成一个项目。

TDD 重点用于授权、生效版本、状态提交、任务恢复、交接等关键行为；简单展示和低风险样式不要求机械地测试先行。Mock 可用于可控故障、接口与回归测试，真实 Agent 能力需要实际试跑验证。

### 2.2 两种“章程”必须分开

- **开发规范**：指导开发者和编码 Agent 如何写代码、管理测试与交付。Spec Kit 的开发 constitution 若启用，属于这一类。
- **组织运行章程**：董事会采用并可修订的运行数据，决定某个 ai-union 的治理与经营授权。

组织修改自己的运行章程，不意味着可以修改开发规范、绕过宿主权限或重写程序。

### 2.3 本轮应留存的工程材料

可沿用仓库现有约定；无约定时采用下列逻辑结构，具体路径可调整：

| 材料 | 作用 |
| --- | --- |
| `specs/001-org-bootstrap/spec.md` | 本轮能力、范围、验收条件，使用本文第 4 节作为起稿 |
| `specs/001-org-bootstrap/plan.md` | 实际选型、模块、接口、数据与风险处理 |
| `specs/001-org-bootstrap/tasks.md` | 按可运行增量拆分的任务及完成证据 |
| 开发决策记录 | 简短记下有影响的选择、原因与替代方案，可置于 plan 内 |
| 测试与 eval 用例 | 能运行的机制测试、真实 Agent 场景及结果判定方法 |
| 运行证据目录或制品 | 实际命令、配置摘要、产物、事件和评测结果；不包含密钥 |
| `HANDOFF.md` 或现有交接文件 | 当前完成度、运行方式、未解决项与下个具体动作 |

这些文件随实现推进。产生文档本身不构成本轮完成。

## 4. 首个迭代 Spec：组织启动与首次协作

迭代标识：`001-org-bootstrap`。

目的：验证目标驱动的组织安排能实际成为成员行动，结果能进入下一轮决定，状态能够延续。

### 4.1 输入与用户体验

输入包括原始目标、已采用的章程、可用 Agent 与工具、资源额度、资产保存位置。目标只需要一句话；环境配置可复用，但配置与授权记录必须明确。

用户启动后能观察到：

1. 系统理解目标与资源条件，形成带依据的初始经营假设。
2. 岗位、成员和工作关系从本次运行中形成。
3. 成员实际执行，某个成员能够使用另一个成员的成果或决定。
4. 产物可以打开、阅读或检查，来源与任务关联可追踪。
5. 交付、阻塞或反馈触发下一轮组织决定，并落实为后续实际动作。
6. 进程停止再启动后，当前责任、已有产物及待办仍然存在。

首轮可以选择当前工具支持的内容形式。支持文本、音频、视频等是产品扩展方向，不要求本迭代同时接通所有媒体与渠道。

### 4.2 本轮必须实现的行为

| 编号 | 行为要求 | 验收证据 |
| --- | --- | --- |
| F01 | 保存目标、组织身份、初始章程和运行资源配置 | 可读取当前状态与采用记录 |
| F02 | 通用启动 Agent 在临时授权内形成初始组织；随后启动权限结束 | 至少两个可区分成员、岗位任职和工作来自实际模型输出，并保存形成依据 |
| F03 | 组织决定包含可执行操作，通过校验后改变正式状态 | 决定、状态版本、工作派发可对应；无效决定有明确拒绝原因 |
| F04 | 对接一个现有 Agent 执行器 | 至少两个成员实际执行，有跨成员成果或决策依赖 |
| F05 | 保存版本化成果、执行事件和证据 | 文件可打开，任务与产物版本可追踪；“完成”声明有实际产物支撑 |
| F06 | 成员结果进入组织循环，形成并执行后续决定 | 后续任务、动作或有依据的等待安排；主线演示至少落实一项后续工作 |
| F07 | 支持最小岗位／任职调整与责任交接 | 一个受控用例证明新责任人能继续未完成工作；演示主线不强制改组 |
| F08 | 支持事件唤醒、持久化复查时间、等待和进程恢复 | 无工作时等待；到期或新事件后继续；重启后责任和待办可恢复 |
| F09 | 提供最小董事会修章入口，更新生效授权 | 受信董事会身份形成修订决定；新行动受新授权影响，历史记录保留旧依据 |
| F10 | 依据岗位与任务组装上下文，支持资料读取与交接 | 上下文清单能列出章程、任职、任务和资料版本；换会话后可继续 |
| F11 | 提供可解释的运行状态 | 展示目标、组织、当前工作、已产出内容、下一步和阻塞原因 |
| F12 | 记录资源使用并遵守配置的有限运行条件 | 调用量、token、可核对费用及额度状态；缺失价格或成本标明未知或估算 |

F09 的修章与 F07 的交接可通过独立用例验证，不要求每次正常经营都触发这两种动作。评测不能奖励无必要的改组或修章。

### 4.3 本轮暂缓内容

- 完整 UNION 平台、多租户商业化、市场、支付结算与复杂管理后台。
- 同时支持多个 Agent 产品、所有内容形式与所有发布渠道。
- 通用投票、董事会席位管理、任意制度编程和完整公司治理产品。
- 向量库、知识图谱、独立记忆服务或复杂分布式基础设施。
- 组织自主改写运行内核、自行添加未授权工具或修改外部评测标准。
- 盈利承诺与以零人工为条件的验收。

本轮允许单组织、单应用、一个真实执行器、单一持久数据库和本地资产目录。逻辑模块可以合并部署。

### 4.4 本轮完成与首版完成的区别

| 状态 | 含义 |
| --- | --- |
| 工程实现完成 | 代码、必要机制测试、启动说明齐备；不能据此声称真实组织能力已验证 |
| 本轮真实试跑通过 | 实际模型完成组织形成、真实协作、产物保存和下一轮行动；有运行记录和产物 |
| 首版体验通过 | 进一步完成真实对外交付、可核验外部反馈，以及据此形成并执行下一轮决定 |

本轮可以在本地或测试环境验证组织能力；模拟反馈必须标为模拟。未接入真实发布或没有外部反馈时，不将其报告为首版验收通过。董事会给出的经营意见也不自动等同于市场反馈。

## 5. 最小工程方案：默认建议，可按仓库调整

本节定义一个可开始实现的方向。它不代表全部技术细节已经被用户冻结。调整时需保持第 1、4 节的产品行为，并记录理由。

### 5.1 先使用单应用、持久状态、可替换执行器

| 模块 | 最小职责 |
| --- | --- |
| 状态与记录 | 目标、章程、岗位、任职、成员、工作、决定、事件、资源与版本 |
| 组织循环 | 收集变化、确定决策责任、组装上下文、调用 Agent、检查与提交决定 |
| 调度 | 派发工作、接收结果、登记唤醒、处理等待和恢复 |
| 执行器适配 | 将统一工作包交给一个已有 Agent，接回实际状态、产物和用量 |
| 资料与上下文 | 版本化文档、证据、记忆条目、基于岗位的查询和任务上下文 |
| 观察入口 | 从实际记录生成状态视图；可先提供 CLI 或简单网页 |

先沿用仓库合理的语言、测试框架与存储方式。无可复用约定时，优先选择执行器已有 SDK 支持良好的语言、单进程服务、支持事务的本地数据库和文件存储；在 plan 中给出确切选择。首轮只评估足以支持当前闭环的少量候选，随即实现。

程序机制与 AI 判断分开：模型提出经营判断和结构化决定；程序负责身份、权限、版本、资源检查以及状态提交与任务派发。模型说明“我有权限”不能替代检查。

### 5.2 最小状态与信息所有权

以下是逻辑对象，可合并表或使用结构化字段，不要求逐对象建立服务：

- `Organization / Goal`：组织身份、原始目标、经授权的目标、阶段目标。
- `Charter / BoardDecision / Policy`：章程正文及可执行字段、采用或修订记录、内部规则和生效引用。
- `Position / Member / Assignment`：岗位、成员稳定身份和任职关系；成员不等于模型会话。
- `Work / Run`：任务、负责岗位与成员、依赖、状态、工作版本、执行尝试及执行器引用。
- `Event / Decision / Wakeup`：事实变化、正式决定、待处理事件、复查条件。
- `Artifact / Evidence / Memory`：版本化产物、来源与回执、带适用条件和不确定性的经验。
- `ResourceUsage`：预算配置、占用与消耗、token 或调用计数、费用来源及估算状态。

组织状态代表当前采用的安排；资料中的判断不因此成为已确认事实。正式知识和成果归组织或工作，成员个人笔记按范围保留。摘要与检索索引可重建，不是唯一事实来源。

### 5.3 通用启动与正常组织循环

启动过程保存目标、已采用章程和资源配置，临时授权一个通用启动 Agent。它提出岗位、任职、决策责任和首批工作。程序校验并落实后，临时启动授权结束；之后按生效内部规则决定问题由谁负责。

正常循环：

1. 保存交付、失败、阻塞、外部反馈、规则变化或到期事件。
2. 读取相关目标、未完成工作、生效章程、内部规则与必要证据。
3. 识别需要处理的问题，区分岗位内执行与组织层决定；合并相关事件。
4. 按生效规则找到决定者，必要时咨询相关成员；董事会保留事项形成议案或等待董事会决定。
5. 使用现有 Agent 提出结构化决定。
6. 检查身份、授权、对象引用、资源、状态版本与支持的操作。
7. 持久保存决定、变更、待派发工作与复查条件，再派发。
8. 成员执行结果成为后续事件；没有可执行事项时等待。

组织循环不等于固定 CEO Agent，不预置“策划—写作—编辑—发布”的行业流程。首版可以只实现按范围指定责任人及有限咨询的规则形式；不支持的规则提案如实报告，不宣布已经生效。

### 5.4 决定协议与允许的变化

建议决定至少包含：

| 字段 | 用途 |
| --- | --- |
| `issue / goal_ref` | 当前问题与目标关系 |
| `evidence_refs` | 所依据的事件、工作与产物版本；标明缺失信息 |
| `actor_ref / assignment_ref` | 决定者及任职依据；真实调用身份由程序绑定 |
| `base_state_version` | 作出判断时的状态版本 |
| `charter_version / policy_version` | 判断所依据的生效规则 |
| `operations` | 建立、修改、分配、暂停、取消或交接哪些对象 |
| `expected_effect` | 希望改善什么、用什么结果检查 |
| `review_trigger` | 交付、事件或未来时间触发条件 |
| `outcome / rationale` | 行动、保持、调查或等待及简要依据 |

首轮操作范围覆盖岗位与成员建立、任职、工作分配及变更、交接、内部规则的受支持字段调整、等待／复查。董事会修章经独立受信入口提交，再进入同一套生效和传播机制。

同一组织的正式状态先采用串行提交，成员执行可以并行。过期决定发生冲突时重新读取与判断，不直接覆盖。决定、状态变更与待派发记录应能一致保存；对派发与结果接收保留稳定标识，处理重试和重复事件。

外部执行副作用与数据库提交不能假设处于同一事务。执行器是否支持取消、重连、去重或查询必须按实际能力处理；不保证无法证明的“恰好执行一次”。状态不明的工作先核对，不盲目重新发布或重复执行。

### 5.5 章程生效与运行边界

初始章程可来自通用模板，但采用记录需要明确董事会身份、版本、临时启动授权与经营边界。测试 fixture 的董事会决定应标为测试；真实运行通过已配置的受信入口记录。Agent 不能通过自行填写 `actor=board` 获得董事会身份。

建议章程正文及可执行字段属于同一版本；正式状态引用生效版本。具体授权值和保留事项从当前规则读取，不散落为永久固定的业务判断。

修章按当前规则形成董事会决定，保存新版本和生效安排，再更新授权与相关上下文。新规则不能追溯性地授权自身修订。受到影响的在途工作明确继续、取消、缩减或交接；新的受控动作在执行前重新检查生效授权，历史行动保留当时依据。

首版只实现受支持的治理字段与变更。出现正文与执行字段冲突、不可解释的授权或未实现规则时，给出明确状态，不能静默扩大权限。

### 5.6 执行器与上下文接口

统一工作包至少包括工作 ID 和版本、负责岗位和成员、任务、相关目标、适用规则、资料引用、可用工具、资源范围、预期产物和回写位置。

执行器至少提供任务提交、状态查询和结果取得。能力声明注明是否支持取消、会话恢复、流式进度、工具限制和用量统计。实际返回映射为已接收、运行、交付、受阻或失败；缺少证据的交付不能冒充已验证成果。

上下文按以下顺序组装：适用目标和规则、岗位与任职、当前任务及依赖、相关增量变化、资料与记忆摘要、进一步读取入口。必需的规则按对象关系读取，不能靠语义检索偶然命中。记录上下文使用的版本清单即可，不要求暴露模型内部思维链。

资料检索先做组织范围、岗位访问和任务关系过滤，再提供元数据与全文查询。首版可支持文本、结构化记录与文件引用；多媒体原件和其转录、摘要分别引用，不能混作同一成果。

## 6. 实施顺序与停止条件

这些步骤属于同一迭代，可以按实际依赖微调。每步都留下可检查的增量，最后集成为第 4 节完整行为。

| 顺序 | 工作 | 本步出口 |
| --- | --- | --- |
| S0 | 核查仓库和执行器，完成本轮 Spec、Plan、Tasks | 实际选型、接口和验收清楚，可开始编码 |
| S1 | 最小持久状态、章程采用、启动事件、决定校验 | 一个真实 Agent 能形成组织安排并写入状态 |
| S2 | 接入工作派发、结果接收、成果与证据保存 | 至少两个成员实际工作，形成跨成员依赖和可打开产物 |
| S3 | 将结果接回组织循环，落实后续决定 | 前轮结果确实影响下一轮工作，并有实际后续行动 |
| S4 | 集成最小交接、修章传播、等待唤醒、重启恢复 | 关键边界用例通过，已有工作和责任可延续 |
| S5 | 完成观察入口、真实试跑、记录与交接 | 能启动、看懂、复现；报告实际完成层级与剩余差距 |

核心行为的测试随 S1—S4 实现同步完成，S5 用于集成与真实试跑，不将全部验证推迟到最后。

遇到不确定技术点，做一个可丢弃的小实验回答具体问题，然后形成选择。不要以探索为由扩建完整平台。真实执行器的接入风险应在前半程暴露。

缺少凭据或外部条件时，继续完成不会受影响的代码、接口测试、运行说明和评测入口。随后集中报告所缺模型服务、配置项或权限及恢复命令；不得把“Mock 跑通”写成“真实 Agent 已验证”。不在未知计费条件下默认展开长期自主运行。

首个迭代完成后交付结果和后续缺口；本文件不要求新 session 自动完成所有后续商业化工作。

## 7. 验证方案

### 7.1 核心机制 TDD

以下按实际实现的风险选择最小有效测试；断言可观察行为，避免只复述实现细节。

| 用例 | 要证明的行为 |
| --- | --- |
| 授权允许与拒绝 | 生效规则允许的动作可执行，越权动作被拒绝；拒绝后正式状态保持一致 |
| 董事会身份与修章 | 普通成员不能冒充董事会；有效修章改变之后的授权；旧决定不会自动沿用失效权限 |
| 决定提交与冲突 | 决定、变更、待派发记录一致；过期冲突有可处理结果 |
| 重复事件与执行恢复 | 重复回执不重复计入成果或推进同一状态；未知执行结果进入核对流程 |
| 任职与交接 | 离任后不再获得该岗位新增权限；未完成责任、历史成果与新负责人连续可查 |
| 文档和上下文版本 | 草稿不替代生效规则；新上下文读取当前版本；旧产物版本仍可追踪 |
| 等待、唤醒与重启 | 等待条件及任务恢复后仍在；无任务时不会无限自唤醒 |
| 资源边界 | 用尽配置额度后按规则暂停；既有用量和恢复条件保留 |

这些测试校验通用运行机制。董事会具体保留哪些事项、额度值等使用章程 fixture 表达，不把某套商业政策永久写死为程序不变量。

### 7.2 真实 Agent 能力评测

先完成一条真实模型烟雾运行，再执行下列最小场景。可以复用同一主线运行和独立受控用例，避免无目的增加模型调用。

| 场景 | 输入与扰动 | 判断依据 |
| --- | --- | --- |
| E1 目标到协作 | 原始目标、通用章程、有限工具与资源 | 组织实际形成，至少两个成员工作，有真实依赖与可打开产物 |
| E2 结果到后续行动 | 前轮产物、交付或受阻事件 | 后续决定引用相关证据，实际任务或行动随之发生；保持原结构允许成立 |
| E3 责任连续 | 在受控用例中使一个成员不可用，或切换其执行会话 | 未完成责任得到继续处理，所需成果和记录未丢失 |
| E4 规则生效 | 受信董事会入口采用一个受支持的章程变更 | 受影响的新行为符合新规则，在途状态明确，历史依据可查 |

E3、E4 的环境变化可以人为注入并明确标注。这些用例衡量系统能力，不代表发生了真实经营事件。不要要求模型在正常场景中为了评测而无理由改组。

本轮首条真实运行证明“能否跑通”。具备预算并需要判断稳定性时，以相同初始条件做少量独立重复运行，记录全部成功与失败；样本不足时明确不作稳定性结论。每次重置独立试验状态，防止前次产物泄漏为本次成功。

### 7.3 评测记录和判定

每次记录：代码版本或工作区快照、模型和执行器版本、目标、章程与配置摘要、工具范围、资源额度、运行标识、事件和动作、产物位置、实际调用及费用、人工介入、结果与失败原因。未知成本和估算成本分别标注。

客观事实优先由程序核对：成员是否执行、文件是否存在且可读、任务是否继续、规则是否生效、回执是否真实。内容质量可按实际内容类型进行人工或模型辅助评价，但与客观完成状态分别报告。

检查实际产物和环境状态，不能仅采信 Agent 的“已完成”声明。验收标准由开发／评测侧维护，运行组织不能自行降低标准。发现评测误判有效方案时可以修订，但记录理由、版本和对既有结果的影响。

## 8. 完成定义与交付报告

### 8.1 首个迭代完成检查

- [ ] Spec、Plan、Tasks 与实际代码一致，重要选择有简短依据。
- [ ] 一个明确支持的执行器可接入，真实调用与 Mock 路径可区分。
- [ ] 组织形成、跨成员工作、产物和下一轮行动有实际证据。
- [ ] 章程生效、交接、等待唤醒与恢复的必要用例通过。
- [ ] 从干净的工作目录按说明能够配置、启动和查看状态。
- [ ] 观察入口明确显示“现在做什么、做成什么、下一步是什么、为何受阻”。
- [ ] 测试命令、实际结果、运行配置摘要和产物位置已保存。
- [ ] 没有预置行业岗位冒充自组织，没有模拟发布冒充真实交付。
- [ ] 费用与失败如实记录，尚未验证的能力明确标注。
- [ ] 已更新交接材料，指出距真实首版验收仍缺少的环节。

缺少真实模型条件时，只可报告工程实现和接口验证完成，明确将真实试跑留为未完成；不得勾选对应证据项。

### 8.2 最终报告模板

1. **这轮做成了什么**：对应 F01—F12，简述用户可见结果。
2. **如何运行和查看**：真实可执行命令、配置入口、输出位置。
3. **验证证据**：运行过的测试、模型试跑、产物和关键限制。
4. **未完成与阻塞**：缺少什么，已完成哪些替代准备，怎样恢复。
5. **下一步唯一优先事项**：从剩余最大缺口出发给出具体动作。

有 Git 环境时遵循仓库约定交付分支或补丁，报告基线和变更范围；不自动合并到主分支或发布。没有远端访问时保留完整本地成果及应用说明。

## 9. 下一轮方向与实际外部行动

本轮通过后，优先推进“真实交付—外部反馈—后续经营行动”。配置用户授权的渠道、账号、资源额度和试验窗口，让组织在这些条件内自主选择内容与经营方式。

可发布文件、测试发布、真实发布分开记录。外部反馈可以来自真实阅读或收听数据、评论、回访等，需可核验并保留来源；没有反馈就记录没有反馈及后续处理。收入和增长作为观察结果，不作为首版最低通过条件。

本文确认的是产品机制与开发路径，不替代具体账号、渠道、预算的实际配置与授权。已有明确授权继续有效；对已授权范围内的日常内容发布不增加逐篇人工审批。需要新增授权时，先完成可审查的具体内容和配置方案，再提出所需决定。

在真实闭环稳定后，再考虑多执行器、多媒体、跨组织协作、平台托管、长期经营和对照 benchmark。单 Agent、预设组织、自组织的比较应使用相同总资源条件，观察结果与成本，避免把增加调用量误当成组织能力提升。

## 10. 执行中的取舍原则

- 每个任务都应能对应首轮体验中的必要行为；与主线无关的支付、平台或基础设施任务暂缓。
- Spec 写清系统提供的能力与边界，具体岗位、经营策略和流程留给组织形成。
- 常规、可逆的工程决定由执行 session 完成并记录；不要把已确认的问题反复交回用户。
- 未知行为先形成可观察的小实验；实现完成度和实际验证程度分开报告。
- 有明确失败或必要门槛才扩展测试；充分验证后继续交付，避免无限增加形式性检查。
- 任何“完成”都对应代码、真实状态或产物证据；计划、组织介绍和角色对话不等于工作已经执行。
- 下次进入同一工程时从代码、Spec、任务状态与交接记录继续，不依赖某次对话仍在上下文中。
