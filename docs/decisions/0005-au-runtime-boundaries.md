# ADR-0005：以明确所有者重组组织运行时，保留单次模型服务边界

日期：2026-11-04。状态：**Proposed；推荐方案，待S00评审采用。未实施。**

## 问题与约束

重写要让产品对象、授权、事务、执行和观察在工程上有统一归属。现有Engine承担多类职责，但已存在组织机制、真实Harness接口、React和独立模型服务。直接全部替换会扩大数据、回执、权限与恢复风险；原样追加无法解决所有者模糊的问题。

约束来自[PRD](../PRD.md)的F01–F12、P15、F16–F20及N01/N03/N04/N05，[019最小契约](../../specs/019-au-core-contract/spec.md)、[048模型方案](../MODEL_ACCESS_ARCHITECTURE.md)及已采用的React方向。

## 备选方案

| 方案 | 收益 | 代价/风险 |
| --- | --- | --- |
| 保持原模块组织，继续在已有入口添加全部逻辑 | 初期改动少 | 请求、事务、规则和适配继续相互耦合，难以对齐需求与测试责任 |
| 新仓库/新技术栈并全面拆分服务 | 可重新塑造所有接口 | 立即引入跨服务一致性、部署和全量迁移；当前没有容量证据证明必要，易复制第二个状态源 |
| 在当前工程中逐用例重组领域、应用与适配边界 | 保留资产和用户流程，同时明确所有者；每片可验 | 迁移期间必须控制依赖方向，防止旧新双写和“只套一层”的无效抽象 |

推荐第三条。保持Python组织运行时和React工程作为迁移载体，模型服务继续单次推理/认证职责；不是规定未来永不能变更语言、存储或部署形态。

## 拟议决定

- 领域层负责AU、章程、岗位/任职、工作/成果等不变量；应用层编排用例、事务和外部执行意图；端口只为实际切片所需依赖建立。
- 适配器实现SQLite、成果文件、已有Harness、模型服务和真实工具，不再复制组织规则。HTTP/CLI和React只调用应用契约及白名单观察投影。
- 一个业务事实只有一个正式写入所有者。每次切换用例要重绑旧调用者并移除该用例重复逻辑；未迁移用例继续由原所有者负责。
- 优先复用单AU持久状态、稳定回执、文件资产及现有事务；跨库采用执行意图/outbox、原请求查询、事件去重和版本隔离，不假装分布式原子事务。
- 保留048的成员Harness与单次模型服务分工、原生状态和单一凭据刷新所有者。模型服务只返回工具调用，由组织侧在有效授权内执行。
- 数据迁移、旧客户端兼容、执行ID/预约/成果历史和回滚窗口必须逐片定义；读取不隐式迁移，未知动作不因版本切换重放。

拟议目录和各层职责由[总体架构](../ARCHITECTURE.md)维护。不得为使目录齐全而先建空壳，或把“所有者清晰”换成所有操作都经一个巨大通用服务。

## 采用前必须回答

1. S00在现有提交上确认首片调用链、数据写入所有者、HTTP/CLI兼容面和真实测试入口。
2. 冻结S01的命令/回执、错误、版本与事务契约，以及旧Engine到新用例的唯一委托位置。
3. 明确本轮保留的数据格式、迁移触发及拒绝条件；有未知外部执行时如何避免采用后重新派发。
4. 对依赖方向、身份/版本校验、重复/迟到回执和事务失败给出可执行的测试方案，接受必要独立复核。

## 影响、回退与状态

采用后的收益是职责和测试边界清晰；代价是每片必须审查旧路径退出，不会靠新增fallback维持长期双轨。若单AUSQLite或当前Harness确实不满足经确认的需求，另写有证据的技术选择和迁移方案，不能默默扩大本ADR。

当前只提交提案；源码和现有数据没有按本ADR变更。采用/修改/拒绝结果需由后续评审记录到本文件及总体架构，随后才把相应切片置为可实施。
