# ADR-0004：以需求追踪、垂直切片和严格TDD组织重写

日期：2026-11-04。状态：**Accepted，仅限本次用户明确选择的开发方法与规划交接范围。** 记录完成不代表产品需求逐项签收、技术提案批准或运行时已实现。

## 背景与来源

用户指出两项原因：“开发时跟chapter不符合，没有想清楚”；“工程过于简陋，没有统一的规划就开始写，乱七八糟”。随后明确提出先补齐可拆解的PRD，在编码前写ADR，按垂直切片拆任务并同步AGENTS，使用TDD循环开发；最后要求形成可交接的point，提交并推送远程分支。

现有[ADR-0002](0002-ai-union-direction.md)、[ADR-0003](0003-react-console.md)与正式开发要求在不冲突的范围继续有效。2026-11-05用户明确采用main的[Chapter V1](../UNION_CHARTER_v1.0.md)，冲突的旧定义由其替代，见[采用记录](../CHARTER_ADOPTION.md)。规划检查点及提交推送已有授权；实际模型开销、生产部署、历史数据删除或仓库可见性另行决定。

## 选择与取舍

| 路径 | 取舍 |
| --- | --- |
| 沿遇到的问题直接追加功能 | 局部启动快，但缺少共同的需求、所有者和验收依据，不能解决本次指出的问题 |
| 先按数据库/后端/前端横向分工，再在末尾集成 | 可并行写大量组件，但长期缺少一个可验证的用户行为，接口偏差和返工容易到末尾才暴露 |
| 先建立统一产品与架构依据，再按用户行为垂直切片 | 需要先澄清关键契约；每片可追踪、测试和交接，符合本次用户选择 |

采用第三条。先统一整体边界和关键契约，再随着实际切片细化内部实现。不会要求先设计完所有未来能力，也不以先做出零散界面替代完整行为。

## 决定

1. [PRD](../PRD.md)是产品需求入口，区分已确认原则、验收提案、实际能力和未决问题；当前稿直接按有效基线重建，旧规划通过Git历史追溯，不再新增旧稿副本。
2. [总体架构](../ARCHITECTURE.md)解释系统职责和契约；重大选择在编码前以Proposed ADR记录，明确采用后再标Accepted。实施/验证状态另列；不把拟议方案写成既成事实。
3. [053任务](../../specs/053-union-rewrite/tasks.md)按用户可观察行为切片，每片包含需求ID、前置决策、正常/异常/恢复、代码所有者、TDD顺序、相关回归及验收证据。
4. 根[AGENTS.md](../../AGENTS.md)保留共同约束，切片引入具体模块边界时再补必要的局部指引。AGENTS引用需求和ADR，不成为第二份产品定义或运行时授权。
5. 后续行为实现使用`TDD Route: strict`，依据为本轮明确用户要求：先看到有意义的RED，再最小实现GREEN，最后保持测试通过地REFACTOR。纯文档整理不为形式编写镜像测试。
6. 真实Agent能力、用户体验、安装和持续运行单独验收。TDD仅证明测试表达的行为，不能替代需求评审或真实业务结果。
7. U编号和状态继续只维护在管理主账；历史工作的完成、阻塞和证据不因重写升级。2026-11-05按用户要求移出旧18张在线建议卡，U-065–U-076直接承接12个V1切片，并映射新在线卡；新需求只依赖本批切片，旧实现仅供核查复用。本轮停止于规划文件可审阅、检查结果明确并提交推送的检查点。
