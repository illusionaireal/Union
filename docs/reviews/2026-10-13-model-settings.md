## 审阅发现

### R1：CLI 在取得派发锁前解析组织默认模型（P2，已修复）

原增量中，CLI 先读取模型 A、构造执行器，再进入 `run` / `watch` 取得派发锁。独立故障注入让另一个受信配置操作在此间取得同一把锁并成功保存模型 B，随后 CLI 仍以 A 执行一次 fixture。该顺序与网页将配置解析放在运行锁内的行为不一致。

实现已改为延迟执行器工厂：`run` / `watch` 取得派发锁后解析组织默认值，显式 `--model` 优先，然后固定该次执行器。独立复验 `test_cli_run_and_watch_resolve_model_after_acquiring_dispatch_lock` 和显式覆盖／空值回退测试通过。交错保存 B 后两个入口均选 B，工厂内再次取得锁会被拒绝，证明解析发生在锁保护范围内。

### R2：CLI 金额硬上限兼容检查与资源更新存在竞态（P2，已修复）

这是同一路径中既有的检查与使用竞态，并非模型设置增量首次引入。修复前 CLI 在锁前确认资源没有 `max_cost`；若受信资源操作随后先取得锁并添加 `max_cost` 与 `cost_reserve_per_call`，延迟工厂仍可构造 Codex 执行器。独立 fixture 注入已复现退出 0、构造工厂一次并新增一次模拟调用，违背该适配器“金额硬上限下拒绝启动”的现有约束。

最终实现将资源兼容检查移入延迟工厂：持有派发锁时读取同次组织状态，先拒绝 `max_cost`，再解析模型并构造执行器。独立复验 `test_cli_rechecks_money_cap_after_acquiring_dispatch_lock` 通过：run / watch 在取得锁前被合法加入金额上限后均退出 2，Codex 执行器未构造，运行记录为 0。R1 的锁顺序测试和 CLI 默认／显式覆盖／空值回退也再次通过。该修正未改变金额计算、既有占用或真实调用授权，R2 已关闭。

## 已核验的行为

- `model` 命令沿用宿主 board 会话、组织目录范围与董事会凭据；观察者和受限 board 不能绕过接口改写其他组织。接口没有凭据、执行器命令、API 地址或宿主路径的配置字段；模型名称只作为单个执行器参数使用，不被解释为地址或路径。
- 配置、版本增量、审计事件与成功回执在同一外层事务中保存。注入配置写入后的失败时，模型和事件一并回滚，拒绝回执仍可查询；旧版本和重复 ID 的不同参数沿用原拒绝机制。
- 保存／清除设置不调用执行器、不预约额度、不修改资源、不启用 Codex，也不取消暂停或核对要求。真实网页启动仍同时要求宿主启用与本次费用未知确认。
- 旧组织没有 `execution_config` 时返回空默认值；保存和清除可持久化并跨服务重启读取。各组织设置独立，快照仅增加允许公开的模型名称。
- 网页 start 首次解析后的模型固定在执行器及 `requested_model` 回执。将组织默认值从 A 改为 B 后重发原请求，仍返回 A，工厂没有再次构造，调用没有增加。本次显式覆盖和空值回退均不改写组织默认值。
- 模型标识有长度及字符限制，并通过 `subprocess` 参数列表传递；不接受以 `--` 开头的额外选项。保存成功仅证明本地配置成功，不证明模型存在、可用、已连接或已执行。`requested_model` 表示请求值，实际模型仍以执行器证据为准。
- 网页新增字段及预览沿用文本转义；观察者仅可查看。Fixture 分支继续使用确定性执行器，不能通过保存模型或本次模型字段变成真实执行。
