# 2026-11-11 Kanban 与 Chapter V1 产品重构审计

> 同日后续：用户已授权执行本审计，实际任务重排与代码修正布置见 [U-109 处置证据](../../evidence/U-109/README.md)。下文保留审计当时的 revision、状态与“尚未执行”边界，不作为处置后的实时状态。

结论：确有方向偏差。直接以原 AU 保留为交付中心的是 #61；#20、#34、#35 也含旧数据或旧入口兼容要求。更普遍的问题是沿用旧工作台，把新产品拆成已有页面中的读取、按钮和接线，再逐项完成工程验收。完整的组织使用体验没有随这些局部交付建立起来。不能把全部 44 张卡说成保旧 AU，也不能把必要的身份、授权、原请求核对和持续责任能力一并废弃。

本次以用户最新决定为准：“我不需要原 AU”；旧前端的 MVP 设计不符合重构要求。原 AU 适配、迁移以及旧页面可用不再构成新产品目标或验收前提。保存历史证据与不擅自破坏现存数据，和继续开发旧产品是不同决定。

## 主要发现

### 1. 高：旧页面结构与回归断言成为重构的隐性约束

**证据。** #34 v4 明确要求“旧兼容入口可用”，并保留“同源公共兼容页脚”；#35 v10 要求“保留原责任工作区、准备态与 legacy 行为”，将范围限定为 `GovernanceWorkspace → WorkPanel` 最小接线。[U-081 证据](../../evidence/U-081/README.md)说明真实 Core `/tasks` 绕过旧 Tasks，工作面板原先在实际入口不可达。它的修复继续保留原 ResponsibilityWorkspace。

部署 PR38 的 `web/console/src/styles.css`、`workspace.css` 与 `dev@266d17d1cf04c5e8a07bdc462f5be1f8cbaebfe5` 字节一致；Layout 仍按 `core_v1/legacy_v0` 分流到新组件或旧页面。CSS 相同本身不能证明没有功能变化，但结合实际路由与用户观察，足以否定“已经完成整体前端重构”的说法。[product-design](../product-design.md)和 [FRONTEND](../FRONTEND.md)区分了历史条目，却主要继续追加各切片说明；本次 44 卡未找到承担整套新信息架构和完整用户旅程替换验收的专门交付。

**影响。** 新后端能力逐个进入旧工作台，用户仍需面对原导航、页面组织和操作方式。协调工作接受了这种交付边界，没有及时检验它是否符合重构目标。

**处置建议。** 退出 #34/#35 的旧 UI 保留约束；重建 V1 产品设计与整体交互契约，按新契约替换旧断言。保留认证、隔离、恢复与下载的行为保障。技术栈继续使用 React，不把复用旧布局作为成功条件。

### 2. 高：同一用户目标被拆成缺乏完整旅程约束的局部交付

实际链条是：#35 显示已有工作 → #38 运行已登记工作 → #59 补目标登记 → #60 补成果采用/交付；#51 和 #62 又分别补模型页、工作页的原请求观察。各部分有价值，但并未同步形成用户从目标到结果的完整使用体验。

**可复核反例。**

- #59/#60 描述明确指出 PR37 的 Core 路由传入 `readOnly + allowExecution`，登记、采用、交付被 `!readOnly` 隐藏；旧 Tasks 的非只读分支不是实际 Core 入口。
- [U-105 证据](../../evidence/U-105/README.md)：实际登记入口缺失导致首轮 15 项 DOM 测试全部 RED；补入口后，旧 U081 浏览器检查仍要求登记入口数量为 0，出现 `1 !== 0`。局部“不提供入口”的旧断言反过来阻挡完整流程，后来才按新契约修正。
- [U-106 证据](../../evidence/U-106/README.md)：真实 HTTP 闭环发现自动 loop 完成后 attempt 仍 running，交付必被拒绝；后来根据原 loop 的持久完成事实，在授权采用事务中正确结束相应 attempt。

**影响。** 分片完成不等于目标已经可用。问题不是禁止拆卡，而是拆卡前未用完整旅程约束范围与集成验收；真实 #39 与父 #22 至今未完成。

**处置建议。** #35/#38/#51/#59/#60/#62 保留可复用能力与已修复边界，按新产品交互重新组合。用户应能表达目标并获得成果、反馈修改、处理异常和查看责任；内部登记、预约、执行准备、采用与交付不应无依据地变成用户逐项操作的常规劳动。依法或依 AU 规则需要人的治理决定，仍按适用范围呈现。

### 3. 高：#61 将旧 AU 延续做成了本次发布的验收中心

**证据。** #61 v13 的结果是“登录/原 AU/任务/成果可读”，验收强调“原业务数据/请求/凭据保留”；固定发布版本为 PR38，而 #60 的成果交付明确不在该发布范围。[U-107](../../evidence/U-107/README.md)记录身份目录兼容处理、原数据回读及后续原账号登录验收。

**判断。** 这是一次有明确授权和实际证据的旧环境发布交付，不能抹成未发生，也不能拿它证明新产品可用。根据用户现在的产品决定，继续围绕原 AU 修兼容、恢复原页面或追加迁移验收，已不应是后续主线。此前强调原 AU 验收，没有回答“重构产品有什么变化”，协调方向确实偏了。

**处置建议。** #61 保留历史发布记录，后续退出产品重构主线；不再把它作为新产品验收。**没有其他卡依赖 #61**，所以不能把所有积压归因于它；移除它也不会自动完成重构。现存数据的保管或删除是单独处置，不在本次审计执行。

### 4. 中：早期治理与工作验收偏向人手操作的控制台

#24 v6 明示“本地治理和人提交文字”的受控验证，示例是把文字记录工作从甲交给乙。#22 checklist 也把“手工工作账本、责任绑定、成果采用与下载”列为已完成基础；自动执行与真实成果是后续补充。治理规则、授权变化和责任交接是必要内核，但人工逐项推动不能代表组织自主工作。

#39 评论 **125** 曾声称“页面级 22-B”10/10 通过，步骤包含 `amend_charter/appoint/start_work/adopt/finish_attempt/deliver`。这只是作者提交的证据声明；其手工 `finish_attempt` 等步骤不能自动证明当前完整页面流程已通过。在线 #39 仍为 backlog，并明确禁止用预置 Work 或旧 driver 成功替代真实页面验收。

**处置建议。** #20/#21/#24/#22 的技术能力继续使用，重新设计准备、治理与业务工作的衔接；以实际参与类别记录人为补救、日常业务劳动、保留治理及自愿参与。测试里的显式命令、ID 和夹具不应直接定义日常产品体验，也不应把单 Agent 有效理解成只需单次任务的 MVP。
