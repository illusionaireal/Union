## 0. 一句话结论

## 3. 主要问题与建议（按优先级）

### P0-1 核心价值链路还是空的：S03 正在变成“人工记账系统”

**现象**

- `ai_union/domain/work.py` 和 `application/work.py` 里没有任何模型调用路径；`start_attempt`、`reserve_step`、`submit_result` 都只能由人在工作页点按钮或手填正文来驱动。
- #22 的验收演示是“输入目标 → **AI** 读取授权目录 → 交出带引用的概览”。到现在交付的是这条链路的全部外围（预算、回执、采用、下载），但链路本身没有。
- 自动代理每轮只挑“本轮能完成的子步骤”。真实模型循环需要凭据和额度，所以它一直在绕开这一步，持续补 UI。按这个节奏，#22 会被做成一个精致但需要人类逐步操作的记账工具，正好和宪章 §1.1“人不应被迫成为调度器”相反。

**建议**

1. **冻结 S03 新增的手工 UI**，下一步只做 *walking skeleton*：复用 S02 已经真实验证过的 `ModelServiceClient` 和两阶段协议，加上 S03.2 的 `list_documents/read_document` 工具，写一个最小的应用层 `run_attempt`，按 `start_attempt → (reserve_step → infer → tool) × N → submit_result → finish_attempt` 的顺序跑完一次执行尝试。先接受“粗糙但真实”。
2. 先用 fake model adapter 做严格 TDD；然后在一个有界授权内跑**一次**真实验收（见 P1-6）。
3. 工作页上“开始执行 / 预约一次调用 / 提交正文”这类按钮，定位为**补救介入入口**（宪章 X-02(d) 的“补救介入”），默认路径应该是系统自动推进。
4. 把 #22 的 checklist 改成：`手工账本（已完成）` / `自动执行循环` / `真实验收一次` / `中断后的 unknown 处理`，让进度一眼可见，不要只散落在 13 条评论里。

### P0-2 自动开发代理缺少质量闸门

**现象**

- `dsh/auto-tick`（deepseek-v4.1-flash）一夜之间往共享集成分支 `rewrite/charter-v1` 直接推了约 18 个提交，没有 PR，也没有独立复核。
- 它自己的评论里承认了两次 TDD 偏差（“组件与其单测同时写成”“本步测试在实现之后写成”），还用“撤掉挂载再恢复”的方式**事后制造 RED**。这正是 AGENTS 里禁止的“为了 RED 而 RED”。
- PR #15 的 CI 浏览器检查 A01 失败。该 PR 自己没改相关脚本，而它整合了自动代理的 S03 提交，所以存在“自动提交引入回归但没人发现”的可能（未确认）。
- 同一个看板账号 `HOME-GOOSE` 先后被 goose 和 dsh/deepseek 使用，身份和执行主体混在一起。这与项目自己主张的“成员、Agent、会话分离”（D-01）不一致。

**建议**

1. 自动代理改为**在自己的分支上提交，再开 PR**；合并条件是 CI 全绿（包括 `console-browser`），并由另一个更强的模型或人做一次复核。至少，auto-tick 每轮推送前要跑一遍 `npm run check` 和 Python 全量测试，失败就不推送并发求助。
2. 每个自动执行主体使用**独立的看板账号**（goose、dsh、codex-home、chatGPT-online 各一个），并清理 `tmp` 这类临时成员。
3. 权限、资金、身份相关的改动（AGENTS 已经要求另一个工程角色复核）在 recipe 中明确列为“自动代理不得独立合入”。
4. 先查清 PR #15 的 A01 失败：在 `0dc9e98` 之前和之后各跑一次 `npm run test:browser`，确认是不是 S03 提交引入的回归。

### P0-3 仓库放在 Synology Drive 同步目录里

**现象**：工作区里已经有 17 个 `*_Conflict*` 文件，包括 `management/project_LAPTOP-…_Conflict.json`（**正式主账的冲突副本**）、多份 docs、`.pyc`，以及 `web/console/src/pages/Models_DESKTOP-…_Conflict.tsx`。同时有多台机器（LAPTOP、DESKTOP、ZBOOK、NAS）和定时代理在同一个同步目录里写入。`.git` 目录被网盘双向同步，可能出现索引或对象损坏、提交“回滚”、两台机器同时改 HEAD 等问题。

**建议**

1. **把 Git 工作区移出网盘同步目录**（例如 `D:\dev\Union`），机器之间只通过 Git 远端同步。网盘只用来放不进 Git 的私有材料。
2. 冲突文件请人工对比后处理。特别是 `project_…_Conflict.json`，要确认里面没有主账遗漏的事实。处理前不要删除。
3. `.gitignore` 加上 `*_Conflict*`，避免冲突文件被误加入提交。

**建议**

### P1-6 真实资源授权成了反复出现的阻塞

#28 卡在“缺合法真实环境、可发送的资料、调用次数和费用上限”，#22 接下来也会卡在同一个地方。每张卡单独申请，代理就只能停下来，或者绕开去做外围工作（见 P0-1）。

**建议（需要项目治理持有人决定）**：发一份**常设的有界开发授权**，例如：指定 1–2 个模型连接；每周 N 次调用；单次输出上限 X tokens；费用上限 Y（明确币种）；只允许读取指定的公开或测试资料目录；超出时创建关注事项而不是阻塞全部工作。把它记录成一份授权依据（Mandate），供 #22/#28 的真实验收引用。这也正好可以作为宪章 S-01“授权内快速试用”的第一次实际使用。

### P1-7 V1 AU 状态是单个 JSON 文档，会成为并发和增长瓶颈

`adapters/core_au_store.py` 用 `state(id=1, data TEXT)` 保存整个 AU 状态。每条命令都要读出整份、修改、做全量 `validate_state`，再整份写回；工具回执、执行尝试和预算步骤都追加在这份文档里。

- 现在单 Agent、少量工作的情况下没问题，而且原子性很好（R-01）。
- 但 S06“一项卡住不挡其他”、R-07 并发，以及长期运行后回执不断累积，都会受这个结构限制：同一 AU 内所有写入串行执行，文档持续变大。

**建议**：先不改，但在 S06 契约里写明迁移点。追加型记录（tool receipts、steps、attempts、results 正文）拆成独立表，并带 AU 事务内的外键；`state` 只保留权威的当前状态。同时给出数量阈值，例如单个 AU 回执超过 1 万条或状态超过 1 MB 时必须迁移。

### P1-8 流程和文档负担过重，影响接手效率

- AGENTS.md 只有 48 行，但每行都很密，充满内部术语（“controlled / unknown / reserved matters / 原请求查询”）。新代理或较弱的模型很难准确执行，自动代理的 TDD 偏差就是一个例子。

  1. AGENTS 增加一个约 15 行的“必须 / 禁止”清单，放在最前面，供自动代理使用；详细规则保留在后面。
  2. evidence 按**卡**（U 编号）建目录，子步骤写在同一个目录的 README 里，不再每步新建目录。
  3. HANDOFF 只保留最近两周，更早的内容归档到 `docs/archive/`。
  4. README 开头写清“5 分钟跑起来并演示 S02”的命令。

### P2-10 分支与合并策略

- `dev` 被称为开发主线，但已经落后 `rewrite/charter-v1` 43 个提交，`main` 落后 90 个。长期运行的重写分支越晚合并，成本越高。
